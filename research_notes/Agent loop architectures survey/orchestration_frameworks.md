# Code-level agent orchestration frameworks: architecture survey (as of 2026-11-03)

Scope: the primitives each framework offers for multi-step, multi-agent loops with humans in the loop, where state lives, how delegation and approval are modelled, what ships for eval/observability, and the limitations authors and critics report. All pages below were opened on 2026-11-03 unless marked otherwise; doc-page dates (ms.date, "published", version banners) are given where the page carried one. Items I could not open are marked UNVERIFIED.

Reader's frame (from the assignment): the user runs multi-pass loops as prose templates inside Claude Code (model-in-session orchestrates, subagents per phase, state in markdown, human gates as lines in a doc). The last two sections compare that against what code frameworks can and cannot express.

## LangGraph (LangChain): graph + state + checkpointer + interrupt()

### Takeaway
LangGraph is explicitly a "low-level orchestration framework and runtime for long-running, stateful agents" whose selling point is explicit control of state and control flow, with durable checkpoints keyed by `thread_id` and `interrupt()`/`Command(resume=...)` for human gates; the main costs are that the pausing node re-runs from its start on resume, and that the abstraction layer is judged heavy by critics.

### Cited Findings
- Stated goal: "LangGraph is a low-level orchestration framework and runtime for long-running, stateful agents." It "does not prescribe prompts or agent architecture"; "Use LangGraph when you need explicit control over state and control flow." Higher-level ready-made loops are pushed to "Deep Agents or LangChain agents." — [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview) (page undated)
- Core abstraction: workflows are graphs of nodes/edges sharing state; "Deterministic and LLM-driven steps can coexist in one graph." Named capabilities: durable execution, streaming, human-in-the-loop, persistence ("Checkpoint state and resume after failures or pauses"), short-term thread state vs long-term cross-session memory. — [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview)
- Observability/deployment: LangSmith is "the platform for tracing, evaluation, prompts, and deployment across frameworks"; "LangSmith Engine detects issues in LangGraph agent traces and proposes fixes" and can open a PR; deployment is "LangSmith Deployment" ("Deploy and scale stateful agents, with visual prototyping in Studio"). The page does not use the name "LangGraph Platform". — [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview)
- Human-in-the-loop mechanics: `interrupt()` "pauses graph execution and returns a value to the caller"; LangGraph "saves the graph state using its persistence layer and waits indefinitely until you resume execution." Requirements: a checkpointer ("use a durable checkpointer in production"), a `thread_id` ("effectively your persistent cursor"), JSON-serializable payload. Resume: re-invoke with `Command(resume=...)` on the same thread; "the value passed to `Command(resume=...)` becomes the return value of the `interrupt` call." — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Resume caveat: the node restarts from its beginning, so "any code before the `interrupt` runs again." Rules: no bare try/except around `interrupt()`; interrupt matching is "strictly index-based" so don't reorder/skip interrupts conditionally; side effects before the interrupt must be idempotent; payloads must be serializable. Static `interrupt_before`/`interrupt_after` are "**not** recommended for human-in-the-loop workflows." Typed `response_schema` needs `langgraph>=1.2.12` and a JSON-Schema dict "does **not** validate resume values against it." — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Approval patterns documented: approve/reject routed with `Command(goto=...)`; review-and-edit (resume value replaces content); tool-call review (`interrupt()` inside a tool; resume payload can approve, cancel, or override args); multiple interrupts resolved by id map; input validation by looping via a conditional edge rather than `while True` inside a node. — [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Persistence limits: `MemorySaver`/`InMemorySaver` "store checkpoints in RAM. When the process restarts, all checkpoints are lost" (use `PostgresSaver`/`SqliteSaver`); "Over long conversations, checkpoints accumulate. This can increase latency and storage costs" (prune/retention); "each subgraph manages its own checkpoint namespace," so a parent may not immediately see subgraph state. — [LangGraph persistence page (resolved from the durable-execution URL)](https://docs.langchain.com/oss/python/langgraph/durable-execution)
- Multi-agent architectures (LangChain docs, which now host the pattern guide): Subagents ("A main agent coordinates subagents as tools"; "stateless by design"; "results flow back through the main agent"); Handoffs ("Agents transfer control to each other via tool calls" that "update a state variable that triggers routing"; "executes **sequentially**—can't research all three languages in parallel"); Router ("A routing step classifies input and directs it to one or more specialized agents"; "**stateless**—each request requires an LLM routing call"); Skills ("Specialized prompts and knowledge loaded on-demand", with the cost that "every subsequent call processes all 6K tokens of skill documentation"); Custom workflow ("Build bespoke execution flows with LangGraph, mixing deterministic logic and agentic behavior"). Claim: "Stateful patterns (Handoffs, Skills) save 40-50% of calls on repeat requests." — [LangChain multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- Authors' argument for low-level orchestration (Harrison Chase, 2025-04-20): "The hard part of building reliable agentic systems is making sure the LLM has the appropriate context at each step." He adopts Anthropic's workflow/agent definitions and prefers asking "how agentic a system is"; argues OpenAI's guide rests on false dichotomies (declarative vs imperative, abstractions vs orchestration, workflows vs agents); LangGraph is "kind of a blend" (nodes/edges are plain functions); goal is "low floor, high ceiling"; agent abstractions accumulate parameters and "obfuscate" what reaches the LLM; persistence, streaming, HITL, observability are "valuable even for simple agents." Comparative claim that the Agents SDK "only lets you do 10%" of LangGraph is unsubstantiated in the post, and the author sells LangGraph. — [How to think about agent frameworks](https://www.langchain.com/blog/how-to-think-about-agent-frameworks)
- Critiques (HN, 2024-10-02, on "Should I Use a Framework to Build an Agent? Code vs. LangGraph vs. Workflows"): jgilhuly: "For experienced developers, framework abstractions can add unnecessary complexity." Defense from nfcampos (LangChain): "In langgraph nodes are just functions that can do whatever you want"; wfhpw separates LangGraph's scheduling/checkpointing/state from LangChain's tool helpers; jgilhuly concedes "at that point, you're not using much of the framework at all." — [HN thread via Algolia API](https://hn.algolia.com/api/v1/items/41722243)
- Forum sentiment (unscored anecdotes, 2025–May 2026): LangGraph "really struggles with complex branching" per one user, and pushes users toward its own patterns; counterpoint that it "shines when you need deterministic state management, human in the loop checkpoints and complex branching logic"; advice to "Start simple, add framework only when you hit a pain point." — [Latenode community thread](https://community.latenode.com/t/current-limitations-of-langchain-and-langgraph-frameworks-in-2025/30994); Reddit snapshots listed in search results (not opened individually; UNVERIFIED beyond the search summary)

### Inferences
- LangGraph's HITL is a durable *pause of a graph node*, not a document gate: the human's answer is a typed value injected into a resumed node, and all control flow around it must be expressed as edges. A fuzzy "proceed if the draft feels ready" gate would have to be encoded as an LLM node that returns a routing label.
- The "node re-runs on resume" rule means every step that precedes a human gate must be idempotent or wrapped; prose loops in a chat session do not have this constraint because the model's transcript is the checkpoint.
- The 2025 "context engineering" essay is the clearest statement of why graph builders exist: to control exactly what the LLM sees at each step. That is also what the user's prose template does, but by instruction rather than by code.

### Gaps
- Could not open the dedicated durable-execution page (the URL resolved to the persistence overview, including the `.md` and JS variants). The durability modes (exit/async/sync) and the `@task` side-effect wrapper are therefore UNVERIFIED here.
- The LangGraph multi-agent page at `/oss/python/langgraph/multi-agent` 404'd; the LangChain-level page was used instead, so `Command(goto=...)` handoff implementation details are only attested via the interrupts page.
- No independent benchmark comparing LangGraph against hand-rolled loops was found beyond the Arize blog referenced in the HN thread (not opened).

## OpenAI Agents SDK: agents, handoffs, guardrails, sessions, tracing

### Takeaway
The SDK is "a production-ready upgrade of ... Swarm" with deliberately few primitives (agents, handoffs/agents-as-tools, guardrails, sessions, tracing); its stance is that LLM-driven orchestration (handoffs) is powerful but "less predictable," code-driven orchestration is "more deterministic and predictable," and the two should be mixed; HITL is a per-tool `needs_approval` pause whose `RunState` can be serialized across processes but gives no exactly-once guarantee.

### Cited Findings
- Design principles: "Enough features to be worth using, but few enough primitives to make it quick to learn" and "Works great out of the box, but you can customize exactly what happens." Primitives: Agents ("LLMs equipped with instructions and tools"), Agents as tools / Handoffs ("allow agents to delegate to other agents for specific tasks"), Guardrails ("enable validation of agent inputs and outputs"), Tracing (built-in, also for "evaluation and fine-tuning"), Sessions ("A persistent memory layer for maintaining working context within an agent loop"). "a very small set of primitives." Swarm relation: "a production-ready upgrade of our previous experimentation for agents, Swarm." HITL is listed only as "Built-in mechanisms for involving humans during agent runs." — [Agents SDK intro](https://openai.github.io/openai-agents-python/) (undated)
- Agent loop: call LLM; final output when "it produces text output with the desired type, and there are no tool calls"; "If the LLM requests a handoff, we update the current agent and input, and re-run the loop"; "If the LLM produces tool calls, we run those tool calls, append the results, and re-run the loop." `max_turns` raises `MaxTurnsExceeded`; `ModelBehaviorError` "when the underlying model (LLM) produces unexpected or invalid outputs." Memory: client-managed (`to_input_list()`, `session`) or OpenAI-managed (`conversation_id`, `previous_response_id`), "pick one persistence strategy per conversation." Durable/long-running: "The integrations below are for durable orchestration when runs may span long waits, retries, or process restarts" — Temporal ("run durable, long-running workflows, including human-in-the-loop tasks") and DBOS. — [Running agents](https://openai.github.io/openai-agents-python/running_agents/)
- Orchestration stance: LLM-driven ("uses the intelligence of an LLM to plan, reason, and decide") vs code-driven; code orchestration "makes tasks more deterministic and predictable, in terms of speed, cost and performance"; LLM orchestration is powerful but less predictable; "the two approaches can be mixed." Agents-as-tools (manager): "A manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`" for bounded subtasks. Handoffs: "A triage agent routes the conversation to a specialist, and that specialist becomes the active agent for the rest of the turn." — [Orchestrating multiple agents](https://openai.github.io/openai-agents-python/multi_agent/)
- OpenAI's guide (PDF, 34 pp.; date not printed in the text — widely dated April 2025, UNVERIFIED here): "Our general recommendation is to maximize a single agent's capabilities first. More agents can provide intuitive separation of concepts, but can introduce additional complexity and overhead, so often a single agent with tools is sufficient." Split "When your agents fail to follow complicated instructions or consistently select incorrect tools." Two multi-agent categories: Manager ("A central 'manager' agent coordinates multiple specialized agents via tool calls") and Decentralized ("Multiple agents operate as peers, handing off tasks to one another"); "In the manager pattern, edges represent tool calls whereas in the decentralized pattern, edges represent handoffs." Manager "is ideal for workflows where you only want one agent to control workflow execution and have access to the user." Human intervention: "Two primary triggers typically warrant human intervention: Exceeding failure thresholds ... High-risk actions: Actions that are sensitive, irreversible, or have high stakes should trigger human oversight until confidence in the agent's reliability grows." — [A practical guide to building agents (PDF)](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- HITL mechanics: `needs_approval=True` or a per-call callable ("Callable approval rules fail closed when the SDK cannot safely inspect the arguments"); applies to `function_tool`, `Agent.as_tool`, `ShellTool`, `ApplyPatchTool`; MCP uses `require_approval`/`tool_config`. When approval is needed "execution pauses, and `RunResult.interruptions`" lists `ToolApprovalItem`s; interruptions from handoffs or nested as_tool runs "surface on the outer run." Resume: `result.to_state()`, `state.approve(...)`/`reject(...)`, `Runner.run(agent, state)`; `always_approve=True` persists a decision. Cross-process: `state.to_json()`/`RunState.from_json()`. Caveats: deserialization "do[es] not authenticate the snapshot or the person submitting it"; approval "does not guarantee exactly-once execution" (use idempotency keys); shell/file-edit sticky decisions "match tool type and name, not the owning agent"; serialized state includes app context so "avoid storing secrets there." — [Human in the loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)

### Inferences
- The SDK itself has no durable scheduler; "pause for days" requires serializing `RunState` yourself or adopting Temporal/DBOS. HITL is therefore a tool-call gate, not a phase gate.
- "Swarm vs orchestrator" is resolved pragmatically: handoffs for conversation routing, agents-as-tools when one agent must retain the user and synthesize; the guide's default is a single agent.

### Gaps
- Sessions/tracing pages were not opened individually; tracing details (spans, exporters) are UNVERIFIED beyond the intro's summary.
- No author-written critique of the SDK's own limits found beyond the third-party claim in the LangChain essay.

## Microsoft Agent Framework (successor to AutoGen + Semantic Kernel)

### Takeaway
MAF (RC Feb 2026, 1.0 GA 2026-04-03, Agent Harness GA July 2026) splits "agents" (open-ended, tool-using) from "workflows" (explicit graphs of typed executors run in Pregel-style supersteps, checkpointed at superstep boundaries), with human input modelled as typed request/response (`ctx.request_info()` / `RequestPort` -> `RequestInfoEvent`) whose pending requests are saved in checkpoints and re-emitted on restore.

### Cited Findings
- Framing and lineage (ms.date 2026-10-23): four areas — Agents, Harness Agent ("An opinionated agent with batteries-included capabilities for long, multi-step tasks — planning and todo tracking, context compaction, file access and memory, don't-ask-again tool approval, and observability"), Workflows ("Functional and graph-based workflows that connect agents and functions through explicit execution paths"), Integrations. "Agent Framework combines AutoGen's simple agent abstractions with Semantic Kernel's enterprise features — session-based state management, type safety, middleware, telemetry — and adds graph-based workflows for explicit multi-agent orchestration." "introduces workflows that give developers explicit control over multi-agent execution paths, plus a robust state management system for long-running and human-in-the-loop scenarios." — [MAF overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)
- When to use which: agent when "The task is open-ended or conversational", "You need autonomous tool use and planning"; workflow when "The process has well-defined steps", "You need explicit control over execution order", "Multiple agents or functions must coordinate." Rule: "If you can write a function to handle the task, do that instead of using an AI agent." — [MAF overview](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)
- Workflow model (ms.date 2026-10-22): "explicit, inspectable execution paths for coordinating code, agents, state, events, and human input." Python has functional (`@workflow`, native `if`/loops/`asyncio.gather`, HITL via `ctx.request_info()`, checkpointing as "Per-`@step` result caching") and graph (`WorkflowBuilder`, edges/conditions, "Superstep-boundary checkpoints", HITL via `RequestInfoExecutor`) APIs; both expose `.as_agent()`. — [Workflow concepts](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/)
- Checkpoints (ms.date 2026-09-16): "Checkpoints are created at the end of each superstep"; capture "The current state of all executors", "All pending messages ... for the next superstep", "Pending requests and responses", "Shared states." Python 1.13.0 adds entry checkpoints so "the complete workflow run [is] replayable." Storage: `InMemoryCheckpointStorage`, `FileCheckpointStorage`, `CosmosCheckpointStorage`. Rehydration "must preserve the topology and executor identities of the workflow that created the checkpoint" (stable agent IDs). Security: "Checkpoint storage is a trust boundary"; Python stores use pickle with a restricted unpickler. — [Checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)
- HITL (ms.date 2026-07-16): "HITL is achieved through the **request and response** handling mechanism." Python: `ctx.request_info()` emits a `request_info` event; `@response_handler` receives `(original_request, response)`; the app loops `workflow.run(stream=True, responses=pending_responses)` until no requests remain. .NET/Go: `RequestPort` ("a typed request/response channel between the workflow and the outside world"). Tool approval in orchestrations emits `function_approval_request` content. "Sequential, concurrent, and group chat orchestrations do not pause for free-form user input on their own"; handoff "is interactive by default." Checkpoints: "pending requests are also saved as part of the checkpoint state. When you restore from a checkpoint, any pending requests will be re-emitted as `RequestInfoEvent` objects." — [Human-in-the-loop](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)
- Orchestrations (ms.date 2026-02-12): Sequential, Concurrent, Handoff ("Agents transfer control to each other based on context"), Group Chat, Magentic ("A manager agent dynamically coordinates specialized agents"). — [Orchestrations](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/)
- Magentic (ms.date 2026-09-04): based on Magentic-One; manager "maintains a shared context, tracks progress, and adapts the workflow in real time"; builder exposes max rounds, max stalls, max resets, and plan review; progress ledger tracks "whether the request is satisfied, whether the team is in a loop, and whether progress is being made"; "Consecutive non-progressing rounds increment a stall counter, and exceeding the configured maximum triggers an automatic reset and replan." HITL plan review via `MagenticPlanReviewRequest` with `approve()` / `revise(feedback)`; Python off by default, .NET on by default. Caveat: "it is untested how well the Magentic orchestration will perform outside of the original Magentic-One design." — [Magentic](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)
- Release timeline: RC 2026-02-19 ([Foundry devblog](https://devblogs.microsoft.com/foundry/microsoft-agent-framework-reaches-release-candidate/), not opened; from search); 1.0 GA 2026-04-03 per a Microsoft Tech Community post (dated 2026-04-28): agents are "long-lived runtime components", workflows are "graph-based orchestration engines"; "If you can solve the task with deterministic code, do that instead of using an AI agent"; Agent Harness = "The execution layer that provides agents with controlled access to the shell, file system, and messaging loops." — [Tech Community post](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/the-future-of-agentic-ai-inside-microsoft-agent-framework-1-0/4510698); Agent Harness GA July 2026 per Azure Updates (search result, UNVERIFIED)

### Inferences
- MAF's "request info" is the most explicit *typed* human gate in the survey: the workflow declares what type it needs back, and the human's answer is routed to the executor by type. It is well suited to structured sign-offs, poorly suited to "read the doc and tell me what you think."
- The Magentic ledgers (task ledger, progress ledger, stall counter) are the code equivalent of the user's markdown state files, but the schema is fixed by the framework.

### Gaps
- Observability page (OpenTelemetry) not opened; telemetry support is attested only via the overview's mention of "telemetry."
- The functional `@workflow` API is marked experimental; no limitations page for it was opened.

## Claude Agent SDK / Claude Code (Anthropic)

### Takeaway
The Agent SDK ships Claude Code's loop as a library: the loop, context compaction, tools, permissions, hooks, subagents (own context, final message only returns), sessions (resume/fork), MCP, skills; the developer supplies the task, the approval UI (`canUseTool`), and any cross-phase state; for orchestration at scale, Anthropic has added "dynamic workflows" (a JS script the runtime executes outside the conversation), explicitly because single-context orchestration suffers "agentic laziness," "self-preferential bias," and "goal drift."

### Cited Findings
- Purpose: "An agent is an application that completes a task by planning its own steps and calling tools ... The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code." Capabilities table: built-in tools, hooks, subagents, MCP, permissions ("Control which tools run automatically, which need approval"), sessions ("Maintain context across exchanges, resume or fork later"), skills/commands/memory loaded from `.claude/`, plugins. Alternatives: Client SDK ("You write the tool loop yourself"), Managed Agents (hosted harness). — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- The loop: "Claude evaluates your prompt, calls tools to take action, receives the results, and repeats until the task is complete." Turns end "until Claude produces output with no tool calls." Controls: `max_turns`, `max_budget_usd` (covers subagents), `effort`, permission modes (`default`, `acceptEdits`, `plan`, `dontAsk`, `auto` ["Uses a model classifier to review actions"], `bypassPermissions`). Context: "Everything accumulates"; automatic compaction "summarizes older history ... Compaction replaces older messages with a summary, so specific instructions from early in the conversation may not be preserved. Persistent rules belong in CLAUDE.md"; a CLAUDE.md "Summary instructions" section steers the compactor; `PreCompact` hook. Sessions: resume restores "the full context from previous turns"; fork to branch; `session_store` adapter for stateless hosts. — [How the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Subagents: "Context isolation: each subagent runs in its own conversation ... only its final message returns to the parent." Parallelization; specialized prompts; tool restrictions. "The only content you pass from parent to subagent is the Agent tool's prompt string." Subagents run in the background by default (`async_launched`); `fork` subagent copies the conversation. Caps: depth default 3 (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), concurrency default 20, `maxBudgetUsd`. Resumable by `agentId` + `resume: sessionId`. Output scanning neutralizes control-tag imitation in subagent reports. "For runs that coordinate dozens to hundreds of agents, use the `Workflow` tool." — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Hooks: "callback functions that run your code in response to agent events." Uses include "Require human approval for sensitive actions." Events: `PreToolUse` (decisions `allow`/`deny`/`ask`/`defer`; `defer` ends the turn with `stop_reason: "tool_deferred"` so you can resume later), `PostToolUse`, `Stop`, `SubagentStart/Stop`, `PreCompact`, `PermissionRequest`, `TaskCompleted` ("Require passing tests before a task closes"), `Elicitation`, plus many TS-only events. "Hooks run in your application process, not inside the agent's context window, so they don't consume context." — [Hooks](https://code.claude.com/docs/en/agent-sdk/hooks)
- Human input: two triggers — tool permission and `AskUserQuestion` — "Both trigger your `canUseTool` callback, which pauses execution until you return a response." "The callback can stay pending indefinitely." For long waits "register a `PreToolUse` hook that returns the `defer` decision ... so the process can exit and resume later from the persisted session." Responses: approve, approve with changes, approve-and-remember (`updatedPermissions`), reject, suggest alternative, redirect via streaming input. Limitation: "`AskUserQuestion` is not currently available in subagents." — [Handle approvals and user input](https://code.claude.com/docs/en/agent-sdk/user-input)
- Dynamic workflows (Claude Code): "A dynamic workflow is a JavaScript script that orchestrates many subagents at once. Claude writes the script ... and a runtime executes it in the background." Comparison table — Subagents/Skills: "Claude, turn by turn" decides, results live in "Claude's context window"; Agent teams: lead agent + shared task list; Workflows: "The script" decides, results in "Script variables", "Dozens to hundreds of agents per run", "Resumable in the same session." "A workflow moves the plan into code." Primitives: `agent()`, `pipeline()`, `parallel()`, `phase()`, `log()`, `args`, `schema` for JSON output. Constraints: "No mid-run user input ... For sign-off between stages, run each stage as its own workflow"; "No direct filesystem or shell access from the workflow itself"; `Date.now()`/`Math.random()` throw so relaunch replays deterministically; 16 concurrent agents default; 1,000 agents per run; resume replays saved results and re-runs from the first changed/failed agent. Saved to `.claude/workflows/`. — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Rationale (blog, 2026-06-02): "When you ask the default Claude Code harness to do a task, it needs to both plan and execute in the same context window ... it can break down over long-running, massively parallel, highly structured and/or adversarial tasks." Failure modes: "Agentic laziness" (declares done "after partial progress, for example addressing 35 of the 50 items"), "Self-preferential bias" (prefers its own results "especially when asked to verify or judge them"), "Goal drift" ("gradual loss of fidelity to the original objective across many turns, especially after compaction. Each summarization step is lossy"). Static workflows "need to work for all edge cases, [so] they are usually more generic." Skill-shipped workflows should be treated "as a template instead of a script that needs to be run verbatim." Costs: "often use more tokens"; "parallelism and specialization have to earn their coordination cost." — [A harness for every task](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- Long-running harness lessons (2025-11-26): sessions "begin with no memory of what came before"; split initializer agent (init script, progress log, first commit) and coding agent ("incremental progress in every session, while leaving clear artifacts for the next session"); state kept in `claude-progress.txt`, git history, and a JSON feature list where agents "may only change the `passes` field" — JSON chosen because the model is less likely to overwrite it than Markdown; one feature per session; failure modes: doing too much at once, "declare the job done" prematurely; generalization beyond web apps "is future work." — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Multi-agent research system (2025-06-13): orchestrator-worker; "multi-agent systems use about 15× more tokens than chats"; token usage explained ~80% of variance on BrowseComp; fits "valuable tasks that involve heavy parallelization", not "domains that require all agents to share the same context"; "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; lead agent saves its plan to memory because context "gets truncated"; subagents write to external storage and pass references; "minor system failures can be catastrophic for agents" so they built resume-from-failure, retries, checkpoints, rainbow deploys; eval: start with ~20 queries, LLM-as-judge 0–1 score plus pass/fail. — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- The SDK's contract is "the loop is given; you own the task, the gate UI, and cross-session state." There is no first-class phase/state machine; state lives in the transcript (sessions), in files the agent writes, and in whatever your hooks persist. This matches the user's current design more closely than any other framework surveyed.
- Anthropic's own evidence (laziness, self-preference, drift after compaction) is the strongest published argument against running a long multi-phase loop as prose in one context — and its remedy (script-held plan, per-phase fresh contexts, adversarial verifiers) is exactly a code-level orchestration layer, just one Claude writes on the fly.
- Dynamic workflows reintroduce the LangGraph-style constraint: no mid-run human input; gates must be between workflow runs.

### Gaps
- `sessions`, `permissions`, and `session-storage` pages not opened; dual-write semantics attested only via the agent-loop page's summary.
- No Anthropic page states a formal limit on how long a prose-driven loop stays faithful; the blog's failure modes are qualitative.

## CrewAI: roles, tasks, crews, flows

### Takeaway
CrewAI pairs autonomous role-based Crews (agents with role/goal/backstory; sequential or hierarchical process) with deterministic event-driven Flows (`@start`/`@listen`/`@router`, Pydantic state, `@persist` to SQLite, `@human_feedback` since 1.8.0); role fields are asserted to "shape the agent's behavior" without measured evidence, and critics (vendor-adjacent) report debugging opacity, token cost, an unresolved hierarchical-delegation bug, and 2026 CVEs.

### Cited Findings
- Crews: "A crew in crewAI represents a collaborative group of agents working together to achieve a set of tasks." Processes: Sequential ("Tasks are executed one after another"); Hierarchical ("A manager agent coordinates the crew, delegating tasks and validating outcomes before proceeding"; `manager_llm` or `manager_agent` required). Memory: "short-term, long-term, and entity memory." JSONC definition recommended; "Only run JSON crew projects from sources you trust." — [Crews](https://docs.crewai.com/en/concepts/crews)
- Agents: Role "Defines the agent's function and expertise within the crew"; Goal "The individual objective that guides the agent's decision-making"; Backstory "Provides context and personality"; the three are required and "shape the agent's behavior." `allow_delegation` default False; `max_iter` default 20; `reasoning` flag; caveats: "A summary can lose details such as exact quotes"; repeated-tool-call cap "The limit of five is fixed." — [Agents](https://docs.crewai.com/en/concepts/agents)
- Tasks: `human_input` = "Whether the task should have a human review the final answer of the agent. Defaults to False"; `guardrail` = "Function to validate task output before proceeding to next task" (string -> `LLMGuardrail`; retried until pass or `guardrail_max_retries`); `context` links task outputs. — [Tasks](https://docs.crewai.com/en/concepts/tasks). Human-input guide: "When enabled, the agent prompts the user for input before delivering its final answer"; no detail on what is shown or how feedback is incorporated. — [Human input on execution](https://docs.crewai.com/en/learn/human-input-on-execution)
- Flows: `@start()` "marks entry points"; `@listen()` listens to another method's output; `@router()` "conditional routing logic based on the output of a method" (labels via `Literal[...]` or `emit=[...]`); `or_()`/`and_()`. State: unstructured (`self.state`) or structured Pydantic; auto UUID `id`. Persistence: `@persist` ("maintain flow state across restarts"); "SQLiteFlowPersistence is the default storage backend"; resume by `inputs={"id": ...}`; fork via `restore_from_state_id`; custom `FlowPersistence`. HITL: `@human_feedback` (CrewAI >= 1.8.0) "pausing flow execution to collect feedback from a human"; with `emit`, "an LLM maps the free-form feedback to one of the listed outcomes." Flows are "deterministic and event-driven" vs autonomous Crews (Atlan's characterization). — [Flows](https://docs.crewai.com/en/concepts/flows)
- Critiques (Atlan, a vendor; checked against the linked primary sources only where stated): "Fastest path to a working multi-agent prototype"; event stream covers lifecycle but "What the event stream does not carry is whether the source data a Crew read was correct"; "a complex hierarchical Crew fans out into many model calls, and default logging is noisy enough that most teams add structured logging"; hierarchical delegation bug [GitHub #4783](https://github.com/crewAIInc/crewAI/issues/4783) (March 2026) where the manager "does not selectively delegate, running tasks in sequence" — "closed as not planned after inactivity" (issue not opened; UNVERIFIED); four 2026 CVEs (CVE-2026-2275/-2285/-2286/-2287) per [CERT/CC VU#221883](https://www.kb.cert.org/vuls/id/221883) (not opened; UNVERIFIED); "Memory doesn't federate across Crews natively." — [Atlan: What is CrewAI](https://atlan.com/know/ai-agent/what-is-crewai/)
- Reviews (May 2026, third-party): "best-in-class for time-to-prototype" but "a tougher sell as the lone framework behind a large-scale system." — search summary citing [similarlabs](https://similarlabs.com/blog/crewai-review) and [aiagentrank](https://aiagentrank.io/blog/crewai-review-2026) (not opened; UNVERIFIED)

### Inferences
- The role/goal/backstory triple is a prompt-template convention, not a runtime primitive: it buys fast authoring and readable team metaphors, and the docs make no quality claim for it. The real control primitives are the Flow decorators and Pydantic state.
- `@human_feedback` with `emit` is the only framework feature found that natively turns free-form human text into a routing label with an LLM — the closest code analogue to a "fuzzy gate."

### Gaps
- The hierarchical-delegation issue and the CVEs were not verified at the primary source.
- No CrewAI-authored statement of limitations beyond scattered caveats.

## Google ADK (Agent Development Kit)

### Takeaway
ADK composes `LlmAgent`s with deterministic workflow agents (Sequential/Loop/Parallel) and a parent/`sub_agents` tree where the model delegates via auto-generated `transfer_to_agent` tools; HITL is an experimental per-tool confirmation (`require_confirmation` / `request_confirmation`) answered as a `FunctionResponse`, with resumability requiring an invocation id and two session services unsupported.

### Cited Findings
- Rationale: build agents that "interweave the non-deterministic functionality of AI models with deterministic code" rather than "relying on non-deterministic AI models to manage the full execution of a task." Triggers to go multi-agent: "Beyond a certain length or complexity of a multiple step set of instructions" a single agent may fail steps; context limits; modularity. — [ADK agents](https://adk.dev/agents/)
- Workflow types: "structuring them as a single, monolithic agent can become challenging to develop, evaluate, and maintain." Template workflows "provide fixed execution logic structures including sequences, loops, and parallel execution"; collaborative workflows (coordinator over sub-agents); graph-based workflows ("a flexible execution graph that can include decision branching"); dynamic workflows ("full programmatic code logic"); agent routing (experimental). — [ADK workflows](https://adk.dev/workflows/)
- Collaboration: "a coordinator agent handles delegation of tasks to one or more subagents"; ADK will "automatically generate a delegation tool for each subagent"; modes chat (default; "require explicit `transfer_to_agent` calls to hand back control"), task (control "automatically returns to the originating agent" on `finish_task`), single_turn (no user interaction, can run in parallel). Limits: parallel agents "cannot see what its peer agents are doing"; parallel only for single-turn; task agents must be leaves; task mode "disabled in graph-based workflows in ADK Python v2.0.0". — [Collaborative workflows](https://adk.dev/workflows/collaboration/)
- Tool confirmation (experimental): a tool can "pause its execution and interact with a user or other system for confirmation." Python: `FunctionTool(..., require_confirmation=True)` or a callable; advanced `request_confirmation(hint, payload)`. Remote: send a `FunctionResponse` named `adk_request_confirmation` with `confirmed` and payload. Resumability: with Resume enabled "you must include the Invocation ID"; otherwise "starts a new invocation with the confirmation response." `DatabaseSessionService` and `VertexAiSessionService` "is not supported by this feature." TypeScript "requires manual implementation of confirmation logic within the tool's `execute` function." — [Tool confirmation](https://adk.dev/tools-custom/confirmation/)

### Inferences
- ADK's hierarchy makes delegation a model decision by default (the coordinator "emits a `transfer_to_agent` call"), with determinism added via workflow agents wrapped around LLM agents — the inverse of LangGraph where the graph is primary.

### Gaps
- Shared `session.state`/`output_key` mechanics, LoopAgent termination (`escalate`), and ADK's eval tooling (`adk eval`) were not opened; UNVERIFIED.
- The ADK docs are mid-reorganization (multiple redirects); version-specific behavior should be rechecked.

## Mastra (TypeScript)

### Takeaway
Mastra offers schema-typed workflows (`createStep`/`createWorkflow`, `.then/.branch/.parallel/.dowhile/.foreach`) with `suspend()`/`resume()` snapshots that "persist across deployments and application restarts," agents usable as steps and workflows as tools, and an experimental LLM-routed AgentNetwork that the docs warn "can use more tokens" and is harder to debug.

### Cited Findings
- Workflows: steps with `inputSchema`/`outputSchema` (Zod/Valibot/ArkType); composed with `.then()` and `.commit()`; "Workflow steps can also call registered agents or import and execute tools directly"; "Use workflows for tasks that are clearly defined upfront and involve multiple steps with a specific execution order." Workflow state "lets you share values across steps"; `restart()` from last active step. Studio: graph view, live step status, time travel. Caveats: run ownership uses an advisory lease that "doesn't fence writes"; on stall "recovery can run that step a second time"; `autoRestartActiveRuns: false` to opt out. — [Workflows overview](https://mastra.ai/docs/workflows/overview)
- Suspend/resume: "Use `suspend()` to pause workflow execution at a specific step"; suspension "saves the current execution state as a snapshot"; snapshots "are stored in your configured storage provider and persist across deployments and application restarts"; `resumeSchema`/`resumeData`; `run.resume()` restarts "from the paused step"; use cases include "requesting human-in-the-loop input", waiting for API callbacks, throttling; "Timers and code responding to human input can also resume a workflow." — [Suspend and resume](https://mastra.ai/docs/workflows/suspend-and-resume)
- Agents vs workflows: agent is "the 'talking brain' of the system: a language model with tools and memory"; workflow: "You define the steps, their order, and the completion criteria"; "We're not asking the model to figure out checkout. We're defining checkout." Agents can run inside workflows; workflows can be tools. — [Agents vs workflows](https://mastra.ai/learn/agents-vs-workflows)
- AgentNetwork (experimental): "Use Workflows when: You need explicit control over execution paths, with predetermined sequences of agent calls and conditional logic"; networks route via an LLM; they "can use more tokens than a well-designed workflow" and debugging is harder "because the LLM makes the routing decisions." — [AgentNetwork reference](https://mastra.ai/en/reference/networks/agent-network) (from search summary; page not opened directly — UNVERIFIED verbatim)

### Inferences
- Mastra's `suspend()` is the cleanest "pause inside a step, resume with typed data" primitive among the TS frameworks; like LangGraph it requires the gate to be a declared step with a declared resume schema.

### Gaps
- Mastra evals/scorers and the control-flow page were not opened.

## Pydantic AI and pydantic-graph

### Takeaway
Pydantic AI treats multi-agent work as a ladder (single agent -> delegation inside a tool -> programmatic hand-off by code or human -> graph state machine -> Deep Agents) and warns that graphs are usually unnecessary; HITL is a run-ending `DeferredToolRequests` output answered in a follow-up run, with the conversation (incl. pending requests) as the only state you must store.

### Cited Findings
- Levels: "roughly five levels of complexity"; agent delegation = "an agent delegates work to another agent, then takes back control"; programmatic hand-off = "application code and/or a human in the loop responsible for deciding which agent to call next"; graph-based control flow "for the most complex cases, a graph-based state machine can be used." Delegation is a tool that calls `other_agent.run(...)`, passing `usage=ctx.usage`. Caveats: cost "cannot be reconstructed from its aggregate token counts"; `run_sync()` can't be used inside a tool; Temporal activities don't propagate usage. — [Multi-agent applications](https://pydantic.dev/docs/ai/multi-agent-applications/)
- pydantic-graph: "an async graph and state machine library for Python where nodes and edges are defined using type hints"; for "when control flow is the hard part"; "If you're not confident a graph-based approach is a good idea, it might be unnecessary"; "graphs are a powerful tool, but they're not the right tool for every job." Nodes are `BaseNode` dataclasses whose `run` return annotation defines edges; `End` ends the run; `graph.iter()` for "inspecting each task as it runs, overriding the next step, or driving the loop manually." — [pydantic-graph](https://pydantic.dev/docs/ai/graph/graph/)
- Persistence (from API docs/tests via search; pages not opened): `iter_from_persistence` "will restore the node and state from state persistence"; `initialize` sets up a run "to be run later, e.g. via `iter_from_persistence`"; `load_next` fetches the snapshot with status `created` and marks it `pending`; `FileStatePersistence` backs a JSON file; issue [#1684](https://github.com/pydantic/pydantic-ai/issues/1684) reported history divergence between File and Full persistence (resolution UNVERIFIED). — [pydantic_graph persistence API](https://pydantic.dev/docs/ai/api/pydantic_graph/persistence) (UNVERIFIED verbatim)
- HITL via deferred tools: `requires_approval=True` or `raise ApprovalRequired`; "When the model calls a tool that requires approval, the agent run will end with a" `DeferredToolRequests` output; resume with `DeferredToolResults` (`ToolApproved`/`ToolDenied`) plus the stored conversation; "the conversation you store is everything you need to resume"; "the requests can't be rebuilt from the messages"; "Approval is not an authorization boundary against an untrusted client." — [Deferred tools](https://pydantic.dev/docs/ai/deferred-tools/)

### Inferences
- Pydantic AI's HITL is the simplest state model in the survey (persist the conversation JSON), at the cost that a "pause" is really "the run ended; start another run with the answers." That is close to how a chat-session prose loop pauses.

### Gaps
- The graph-builder/persistence pages 404'd at every URL tried (`/graph/persistence/`, `/graph/graph-builder/`, raw GitHub); the cross-process HITL example is attested only by search snippets.

## Vercel: AI SDK agents, Workflow SDK, and eve

### Takeaway
Vercel stratifies: `ToolLoopAgent` (in-request loop, "does not persist execution checkpoints"), `WorkflowAgent` (loop inside a durable Workflow run; `needsApproval` produces an approval request and a hook can suspend the run), and eve (a "filesystem-first" agent framework where the `agent/` directory defines instructions, tools, skills, subagents, channels, schedules; sessions run as Workflow SDK runs, park "for as long as it takes — seconds or days" on approval, and replay completed steps).

### Cited Findings
- Comparison (2026-11-02): "`ToolLoopAgent` does not persist execution checkpoints"; `WorkflowAgent`: "Model calls run as durable steps", tools marked `'use step'` get checkpointing/retries, `needsApproval` "produces an approval request without executing the tool", "Use it when completed model calls and tool results must survive an interruption, or when orchestration spans hours or days" (Workflow 5.1+); eve: "eve sessions are durable by default", "built-in channels for platforms such as Slack and GitHub", eval runner, subagents and schedules each "has its own folder in the `agent/` directory"; status 1.0.0-rc.1. — [Choosing between eve, AI SDK agents, and WorkflowAgent](https://vercel.com/kb/guide/eve-vs-ai-sdk-agents-vs-workflowagent)
- Workflow SDK (page last_updated 2026-09-04): "`'use workflow'` and `'use step'` directives"; "Resumable: Pause for minutes or months, then resume from the exact point"; "Durable: Survive deployments and crashes with deterministic replays"; "No YAML or state machines"; sleep and hooks "wait for external events"; every step/input/output recorded for observability; human approval via Chat SDK + Workflows ("pause for human approval"). — [Vercel Workflows](https://vercel.com/docs/workflow)
- eve files: `instructions.md` (base system prompt, "A flat file or directory of `.md` and `.ts` files"), `agent.ts` (model, compaction), `tools/`, `skills/` ("on-demand procedures ... flat Markdown, module-backed skills, or packaged skills"), `subagents/` (nesting supported), `channels/`, `schedules/` (modules or "Markdown prompts with `cron` frontmatter"), `memory`, `sandbox`, `hooks/`, `connections/`; evals "live beside `agent/`, not inside it." — [eve agent files](https://eve.dev/docs/reference/agent-files)
- eve execution model: session / turn / step ("a saved checkpoint inside a turn, by default one model call plus its inline tool calls"); "Your code runs inside a managed step"; "Completed steps never re-run; eve replays the recorded result"; "An interrupted step runs again from the checkpoint before it, so model calls in that step can run again"; parked turns hold "no compute until the input arrives, even much later"; `defineState` survives restarts; local persistence under `.eve/.workflow-data`; subagents: "Nothing crosses the boundary implicitly." Not exactly-once: give irreversible tools "a stable operation ID"; only the eve version that started a run can replay it ("stranded sessions"); drivers before eve 0.45 can't be imported. The page does not itself use the phrase "filesystem-first." — [Execution model and durability](https://eve.dev/docs/concepts/execution-model-and-durability)
- eve HITL: `approval` field with `never()` (default — "tool calls may execute without human approval"), `once()`, `always()`, `auto()` (a decision model classifies `clear`/`caution`), or a predicate; "The run waits durably, for as long as it takes — seconds or days"; answers via `inputResponses` keyed by `requestId` or a follow-up message matching an option; an unrelated follow-up "cancels the turn's pending approval, so the call doesn't run"; `ask_question` tool is opt-in; "Submitting an answer does not confirm approval." — [eve human-in-the-loop (unpkg 0.77.0 docs)](https://unpkg.com/eve@0.77.0/docs/tools/human-in-the-loop.md)
- On Vercel: "eve checkpoints progress between steps and resumes pending work after interruptions. Waiting for approval or user input suspends the workflow until that input arrives"; "an interrupted step can execute again. Make tool actions that send emails, create records, or charge customers idempotent"; Agent Runs "shows conversations, tool calls, token usage." — [eve on Vercel](https://vercel.com/docs/frameworks/agents/eve)
- Preview status: launched 2026-06-17, "framework, APIs, documentation, and behavior may change before general availability"; "eve agents may operate with permissive settings, including tool execution without human approval." — search summary citing [vercel.com/docs/eve](https://vercel.com/docs/eve) and third-party posts (UNVERIFIED verbatim)

### Inferences
- eve is the framework closest to the user's "state in files" instinct: prompts, skills, schedules and subagents are files, and the durable session is a replayable event log. But its filesystem is for *configuration*; run state is an event-sourced Workflow run, not a document.
- The replay model (completed steps return recorded results) is the same idea Claude Code's dynamic workflows use for resume.

### Gaps
- The eve "filesystem-first" tagline is Vercel marketing language; eve's own concept page did not define it.
- eve evals and `defineWorkflowTool` details not opened.

## smolagents (Hugging Face)

### Takeaway
smolagents defines agency as a spectrum ("AI Agents are programs where LLM outputs control the workflow"), argues for code-as-action (`CodeAgent`) over JSON tool calls, advises "regularize towards not using any agentic behaviour," and models multi-agent as a manager `CodeAgent` with `managed_agents` callable like tools.

### Cited Findings
- "AI Agents are **programs where LLM outputs control the workflow**"; agency levels from "Simple processor" (no impact on flow) through Router, Tool call, Multi-step Agent (`while llm_should_continue(memory): ...`), Multi-Agent, Code Agents. "If that deterministic workflow fits all queries, by all means just code everything! ... it's advised to regularize towards not using any agentic behaviour." "If the pre-determined workflow falls short too often, that means you need more flexibility." — [Intro to agents](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents)
- Why a framework: tool calling needs a parser + system-prompt format; a multi-step loop needs memory; "we need error logging and retry mechanisms"; "All these elements need tight coupling." Code actions: "having the LLMs actions written as code snippets is a more natural and flexible way"; benefits "Composability", "Object management", "Generality", "Representation in LLM training data." — [Intro to agents](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents)

### Inferences
- smolagents has no durable state or HITL primitive in the pages opened; it is a loop library, not an orchestration runtime.

## DSPy: programming, not prompting

### Takeaway
DSPy (3.4.1 banner) replaces hand prompts with typed signatures composed in Python modules, then "compiles" the program against a metric and training set with optimizers (GEPA, MIPROv2, BootstrapFewShot, BootstrapFinetune); it is an optimization layer, not an orchestration/HITL runtime, and its known failure modes are metric misspecification and overfitting small train sets.

### Cited Findings
- "Program, don't prompt, your LLMs"; signatures = "typed inputs and outputs instead of managing messy prompts"; modules (`Predict`, `ChainOfThought`, `ReAct`) control "how your signature executes"; custom `dspy.Module` with plain Python control flow; optimizers "compile your program against a metric"; saved as JSON (`opt.save("rag.v2.json")`); example F1 0.41 -> 0.63 at a stated $2.18 compile cost. GEPA ("Reflective Prompt Evolution", July 2025), MIPROv2 (June 2024). — [dspy.ai](https://dspy.ai/)
- Philosophy: "a bet on 'writing code instead of strings'"; "DSPy separates these concerns and automates the lower-level ones until you need to consider them"; stages: define task (inputs/outputs), start with one `ChainOfThought`, add complexity "incrementally based on observations", record easy and hard examples "useful when you are doing evaluation and optimization later"; "building the right control flow is crucial." — [programming overview (GitHub source)](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/learn/programming/overview.md)
- Optimizer choice: "Zero-config baselines (LabeledFewShot, BootstrapFewShot) cost almost nothing"; "Search-based optimizers (BootstrapRS, MIPROv2, GEPA) cost real money"; GEPA needs `Prediction(score, feedback)`; "Picking the wrong metric shape for the wrong optimizer is the most common configuration mistake"; "DSPy doesn't introspect your task or LM to pick an optimizer"; "A demo set learned on 50 training examples describes that specific trainset. An instruction rewrite, by contrast, captures patterns at a level above the examples and tends to transfer"; "`.compile()` is expensive — GEPA and MIPROv2 can spend hundreds of dollars"; "Treat finetune as the last lever, not the first." — [choosing an optimizer (GitHub source)](https://raw.githubusercontent.com/stanfordnlp/dspy/main/docs/docs/diving-deeper/choosing-an-optimizer.md)
- Critiques (practitioner blogs via search; not opened): ~30 labeled examples minimum, 300 better; a GEPA rewrite raised train accuracy 90%->95% but cut held-out 95%->85%; two of three "baseline failures" were metric bugs; "creative, open-ended tasks with subjective quality give the optimizer no score to maximize." — search summary of [agentpatterns.ai](https://agentpatterns.ai/patterns/agent-design/dspy-programmatic-prompt-optimization/) and [theneuralbase](https://theneuralbase.com/dspy/learn/intermediate/minimum-dataset-size-for-optimization/) (UNVERIFIED)

### Inferences
- DSPy is orthogonal to the orchestration question: it could optimize the per-phase prompts of a prose loop *if* each phase had a scalar metric and a few dozen labeled examples — which document-centric, judgment-heavy phases usually lack.

### Gaps
- The dspy.ai docs site served only navigation stubs for `/learn/...` and `/diving-deeper/...`; GitHub sources were used instead.

## Cross-cutting: workflow vs agent, deterministic vs model-chosen steps, long horizons, where human approval belongs

### Takeaway
Every vendor has converged on Anthropic's December 2024 dichotomy (workflows = "predefined code paths", agents = model "dynamically direct[s]" its process), with the uniform advice to start with the simplest system; long-horizon failure is attributed to context (truncation/compaction loss, drift, laziness, self-preference) and cost (~4x per agent, ~15x for multi-agent), with the remedies being external state, fresh contexts per subtask, and script-held plans; human approval is placed on irreversible/high-risk tool calls and at plan sign-off, and every durable framework warns that approval does not make the gated action exactly-once.

### Cited Findings
- Definitions (2024-12-19): "Workflows are systems where LLMs and tools are orchestrated through predefined code paths"; agents are systems where the LLM "dynamically direct[s] their own processes and tool usage"; patterns: prompt chaining, routing, parallelization, orchestrator-workers ("a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results"), evaluator-optimizer. Frameworks "create extra layers of abstraction that can obscure the underlying prompts"; "start by using LLM APIs directly"; agents "can then pause for human feedback at checkpoints or when encountering blockers"; add complexity "only when it demonstrably improves outcomes." — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Same dichotomy restated by MAF ("If you can write a function to handle the task, do that"), Mastra ("We're not asking the model to figure out checkout. We're defining checkout"), smolagents ("regularize towards not using any agentic behaviour"), OpenAI ("maximize a single agent's capabilities first"), LangChain ("how agentic a system is"). — sources above
- Against multi-agent (Cognition, 2025-06-12): "Share context, and share full agent traces, not just individual messages"; "Actions carry implicit decisions, and conflicting decisions carry bad results"; Swarm and AutoGen "actively push concepts which I believe to be the wrong way of building agents"; "running multiple agents in collaboration only results in fragile systems"; default "a single-threaded linear agent"; for long tasks a compression model, but "You will still eventually hit a limit." — [Don't build multi-agents](https://cognition.com/blog/dont-build-multi-agents)
- For multi-agent when parallelizable (Anthropic, 2025-06-13): ~15x tokens; "excel at valuable tasks that involve heavy parallelization"; not for "domains that require all agents to share the same context." — [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Long-horizon failure modes named by Anthropic (2026-06-02): agentic laziness, self-preferential bias, goal drift ("Each summarization step is lossy"). — [A harness for every task](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/); and SDK docs: "Compaction replaces older messages with a summary, so specific instructions from early in the conversation may not be preserved." — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Long-horizon remedy = external state artifacts: progress file, git, JSON feature list, one feature per session. — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Where approval belongs: OpenAI — "High-risk actions: Actions that are sensitive, irreversible, or have high stakes should trigger human oversight"; failure thresholds. — [OpenAI guide PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf). MAF Magentic — plan review before execution (approve/revise). — [Magentic](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic). Claude Code workflows — "For sign-off between stages, run each stage as its own workflow." — [Dynamic workflows](https://code.claude.com/docs/en/workflows). LangGraph — tool-call review inside tools; "approve or reject" nodes. — [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts). eve — default is no approval; `auto()` delegates the decision to a classifier model. — [eve HITL](https://unpkg.com/eve@0.77.0/docs/tools/human-in-the-loop.md). Claude Code `auto` permission mode "Uses a model classifier to review actions." — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Non-exactly-once warnings: OpenAI ("does not guarantee exactly-once execution"), LangGraph ("any code before the `interrupt` runs again"), eve ("Recovery doesn't make external effects exactly-once"), Vercel ("an interrupted step can execute again"), Mastra ("recovery can run that step a second time"). — sources above

### Inferences
- The "deterministic steps vs model-chosen steps" question is, in every framework, answered by composition: deterministic skeleton (graph/workflow/script) with model-chosen steps inside nodes. The disagreement is only about which layer is primary.
- The consensus on gates is "gate the irreversible tool call and the plan," not "gate each phase transition." Phase gates are implemented as run boundaries (end a run, start a new one), which is what a prose loop does by stopping and waiting for a message.
- Cost framing: every durable framework replays or re-runs; prose loops in a session "replay" for free because the transcript is the log — until compaction destroys it.

### Gaps
- No controlled study comparing graph-orchestrated vs prose-orchestrated loops on long-horizon fidelity was found; all long-horizon claims are vendor engineering posts.

## What these frameworks cannot express: NL-defined processes, fuzzy gates, document-centric state

### Takeaway
No surveyed framework has a primitive for "the process is a prose document the model follows"; processes are code (graphs, decorators, directives, scripts), gates are typed values on tool calls or request ports, and state is a typed object, a checkpoint blob, or an event log; the closest partial fits are CrewAI's `@human_feedback(emit=...)` (LLM maps free text to a label), eve's Markdown skills/schedules and `instructions.md`, Claude Code skills/CLAUDE.md, and Anthropic's own file-based progress artifacts.

### Cited Findings
- Process-as-code everywhere: LangGraph nodes/edges ([overview](https://docs.langchain.com/oss/python/langgraph/overview)); MAF "explicit, inspectable execution paths" ([concepts](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/)); CrewAI Flow decorators ([flows](https://docs.crewai.com/en/concepts/flows)); Mastra `createWorkflow` ([overview](https://mastra.ai/docs/workflows/overview)); Vercel `'use workflow'` ("No YAML or state machines") ([workflows](https://vercel.com/docs/workflow)); Claude Code workflow = "a JavaScript script" and "A workflow moves the plan into code" ([dynamic workflows](https://code.claude.com/docs/en/workflows)).
- Prose that frameworks do accept: Claude Code skills ("Instructions Claude follows"; "Who decides what runs next: Claude, following the prompt") and the explicit statement that skill-shipped workflows are "a template instead of a script that needs to be run verbatim" ([dynamic workflows](https://code.claude.com/docs/en/workflows); [blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)); eve `instructions.md`, Markdown skills, Markdown schedules with cron frontmatter ([agent files](https://eve.dev/docs/reference/agent-files)); LangChain "Skills" pattern ([multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)); CrewAI YAML/JSONC role definitions ([crews](https://docs.crewai.com/en/concepts/crews)).
- Fuzzy gates: CrewAI `@human_feedback` with `emit` — "an LLM maps the free-form feedback to one of the listed outcomes" ([flows](https://docs.crewai.com/en/concepts/flows)); eve `auto()` approval classifier ([eve HITL](https://unpkg.com/eve@0.77.0/docs/tools/human-in-the-loop.md)); Claude Code `auto` permission mode ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)); MAF Magentic progress ledger (LLM judges "whether progress is being made") ([Magentic](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)). All others require a typed resume value: LangGraph `Command(resume=...)` ("does **not** validate resume values" against a JSON schema) ([interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)); MAF typed `response_type` ([HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)); Mastra `resumeSchema` ([suspend](https://mastra.ai/docs/workflows/suspend-and-resume)); Pydantic `ToolApproved`/`ToolDenied` ([deferred tools](https://pydantic.dev/docs/ai/deferred-tools/)); OpenAI `approve`/`reject` ([HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)).
- Document-centric state: no framework stores run state as a human-edited document. Anthropic's long-running harness uses files (`claude-progress.txt`, git, feature JSON) *as* state and notes JSON was chosen because the model is less likely to overwrite it than Markdown ([effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); Anthropic's research system has subagents "write outputs to external storage and pass lightweight references" ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)); Claude Code sessions persist transcripts and `resume` restores "the full context" ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)); CrewAI persists Pydantic state to SQLite ([flows](https://docs.crewai.com/en/concepts/flows)); eve: `defineState` plus per-session sandbox files ([execution model](https://eve.dev/docs/concepts/execution-model-and-durability)).

### Inferences
- What code buys over prose, per the sources: (1) the plan survives outside the model's context (script variables, checkpoints), so drift/laziness/self-preference are structurally bounded; (2) deterministic replay/resume after crash or days-long waits; (3) typed, validated hand-offs and gates; (4) tracing, cost caps, concurrency caps, budget caps; (5) parallel fan-out at hundreds of agents.
- What prose buys over code, per the same sources: (1) the process can be "a template instead of a script"; the model adapts steps to the case (Anthropic's own argument for dynamic over static workflows); (2) gates can be judgment calls read from a document; (3) state is readable and editable by the human mid-loop without a schema; (4) zero framework surface — the "start with the API directly" advice. The price is the documented long-context failure modes and the lack of guaranteed replay.
- A hybrid already exists in the user's tool: Claude Code's workflow runtime executes a script whose agents can be prompted with prose templates, whose results can be JSON-validated via `schema`, and whose phase boundaries become human gates by ending the run. The missing piece is mid-run human input ("No mid-run user input").

### Gaps
- No framework documentation discusses "the model follows a natural-language SOP" as a first-class mode; this is an absence, not a stated limitation.

## What would stop this from managing something other than software/chat

### Takeaway
The frameworks are domain-agnostic at the graph/loop layer, but every durable primitive (replay, checkpoint, approval) presumes idempotent, programmatic tools; every HITL primitive presumes a typed answer to a tool-call or request-port; every observability story presumes traces of model/tool calls; and the published long-horizon evidence is drawn almost entirely from coding, research-browsing, and customer-service chat. Managing a non-software process (an editorial pipeline, a grant review, a construction schedule) would hit: tools that are not idempotent and cannot be replayed, gates that are judgments on documents rather than booleans, state that lives in documents humans edit, and no evaluation metric.

### Cited Findings
- Replay/idempotency assumptions: "Make tool actions that send emails, create records, or charge customers idempotent so a retry doesn't repeat the external action" ([eve on Vercel](https://vercel.com/docs/frameworks/agents/eve)); "any code before the `interrupt` runs again" ([LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)); "does not guarantee exactly-once execution" ([OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)); "Give irreversible tools a stable operation ID" ([eve execution model](https://eve.dev/docs/concepts/execution-model-and-durability)).
- Typed-gate assumptions: MAF `request_info(request_data, response_type=int)` ([HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)); Mastra `resumeSchema` ([suspend](https://mastra.ai/docs/workflows/suspend-and-resume)); Pydantic `DeferredToolResults` ([deferred tools](https://pydantic.dev/docs/ai/deferred-tools/)); Claude Code `AskUserQuestion` limited to "1-4 questions with 2-4 options each" and "not currently available in subagents" ([user input](https://code.claude.com/docs/en/agent-sdk/user-input)); Claude Code workflows "No mid-run user input" ([workflows](https://code.claude.com/docs/en/workflows)).
- Domain of evidence: Anthropic's harness demo "targets full-stack web apps. Generalizing to other fields, such as scientific research or financial modeling, is future work" ([effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); Claude Code workflow examples are audits, migrations, PR review, research ([workflows](https://code.claude.com/docs/en/workflows)); MAF: "it is untested how well the Magentic orchestration will perform outside of the original Magentic-One design" ([Magentic](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/magentic)); OpenAI's HITL examples are "customer service" and "a coding agent" ([OpenAI guide PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)); Cognition's examples are Flappy Bird / coding ([Don't build multi-agents](https://cognition.com/blog/dont-build-multi-agents)).
- Evaluation assumptions: DSPy needs "a metric" and labeled examples; "creative, open-ended tasks with subjective quality give the optimizer no score to maximize" (search summary, UNVERIFIED) ([dspy.ai](https://dspy.ai/)); Anthropic's research eval used LLM-as-judge with a 0–1 score, and still needed human testing to catch "SEO content farms outranking authoritative sources" ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)); CrewAI's event stream "does not carry ... whether the source data a Crew read was correct" ([Atlan](https://atlan.com/know/ai-agent/what-is-crewai/)).
- Tooling assumptions: Claude Agent SDK's built-in tools are file/shell/web ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)); eve's sandbox is for "shell, file, and process work" ([execution model](https://eve.dev/docs/concepts/execution-model-and-durability)); MAF Harness provides "controlled access to the shell, file system, and messaging loops" ([Tech Community](https://techcommunity.microsoft.com/blog/azuredevcommunityblog/the-future-of-agentic-ai-inside-microsoft-agent-framework-1-0/4510698)).
- Security/trust boundaries that presume an engineering operator: "Checkpoint storage is a trust boundary" with pickle deserialization ([MAF checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints)); "Approval is not an authorization boundary against an untrusted client" ([Pydantic deferred tools](https://pydantic.dev/docs/ai/deferred-tools/)); eve default "tool calls may execute without human approval" ([eve HITL](https://unpkg.com/eve@0.77.0/docs/tools/human-in-the-loop.md)).

### Inferences
- Concretely, for a non-software process the blockers are: (a) the unit of work is a document revision, not a tool call, so tool-level approval gates the wrong thing; (b) humans want to edit the artifact and have the loop continue from the edited artifact, which only transcript-/file-based state (Claude Code sessions, eve sandbox files, CrewAI state via `restore_from_state_id`) supports, and none validates; (c) "done" is a judgment, so the loop needs an LLM judge node or a human gate at every phase — exactly the place where frameworks say "end the run and start another"; (d) there is no scalar metric, so DSPy-style optimization and most eval tooling do not apply; (e) the published failure-mode evidence (laziness, drift, self-preference) was measured on code and research tasks, so its magnitude elsewhere is unknown.
- The frameworks that would transfer most easily are the ones whose state is a readable file or conversation and whose gates are run boundaries: Claude Agent SDK/Claude Code (sessions + files + skills), eve (Markdown instructions/skills/schedules, durable parking), and Pydantic AI (persist-the-conversation). Graph frameworks transfer only after the process is formalized into typed steps.

### Gaps
- I found no published case study of any of these frameworks managing a long-horizon, document-centric, non-software process (e.g., legal, editorial, operations) with human sign-offs; the absence may reflect search limits rather than non-existence.
- No source quantifies how often human gates fire in production deployments or how long runs stay parked.
