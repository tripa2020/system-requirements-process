# Durable execution and workflow engines as a substrate for AI agent loops (as of 2026-11-03)

Scope note: every claim below is sourced to a page that was actually opened unless tagged UNVERIFIED (seen only in a search snippet or secondary summary). Dates are those printed on the page or in the snippet. Vendor pages are promotional; where a claim is only vendor marketing it is labelled as such. Several documentation URLs returned 404 in this session (Temporal `/workflow-definition/versioning`, Cloudflare `/workflows/platform/limits/`, Cloudflare `/agents/api-reference/human-in-the-loop/`, Hatchet `/guides/ai-agents`, DBOS `/explanations/why-dbos-agents` returned empty); alternates were used and are named.

A shared vocabulary that recurs across all engines (my framing, grounded in the cited pages):
- **Workflow / orchestrator function**: the long-lived control flow. Must be deterministic (Temporal, DBOS, Restate, Vercel, Inngest code-outside-steps) because the engine re-executes it to rebuild state.
- **Step / activity / `ctx.run`**: the unit whose result is journaled; anything non-deterministic (LLM call, HTTP, time, random) goes here. Retried, memoized, never re-run after success.
- **Durable wait**: timer (sleep) or wait-for-external-input (signal / event / hook / awakeable / token / `recv`). The process is not resident while waiting.
- **Versioning**: what happens to in-flight runs when the orchestrator code changes. Every engine treats this as a hazard requiring explicit handling.

## Key Question 1: Temporal (workflows, activities, signals, determinism, AI-agent guidance 2025-26)

### Takeaway
Temporal is the reference implementation of deterministic-replay durable execution: the workflow function is re-executed against an append-only Event History and any divergence is a hard "non-deterministic error". LLM calls, tools and MCP access must be Activities; human gates are Signals/Updates awaited via `wait_condition` with no stated upper bound; code changes mid-run require patch markers or Worker Versioning; histories are capped at 51,200 events / 50 MB, which forces `Continue-As-New` for long-lived agents.

### Cited Findings
- Definition and determinism rule: a Workflow is "a sequence of steps written in a general-purpose programming language"; workflow code must "make the same Workflow API calls in the same sequence, given the same input." Non-deterministic work "such as API calls, LLM/AI invocations, and database queries belongs in Activities." Branching on local time or random numbers inline is unsafe; use replay-safe SDK APIs. — [Temporal docs: Workflow Definition](https://docs.temporal.io/workflow-definition)
- Replay mechanics: on replay "emitted Commands are compared with the existing Event History"; a mismatch causes the Execution to "return a _non-deterministic_ error." Commands that must not be reordered/added/removed without versioning: timers, Activities, Child Workflows, signalling external Workflows, ending the Execution, `Patched`/`GetVersion`, search attributes, memos, `SideEffect`. — [Temporal docs: Workflow Definition](https://docs.temporal.io/workflow-definition)
- Failure model: "The only reason a Workflow Execution might fail is due to the code throwing an error or exception"; Workers can fail or restart without affecting the Workflow. Activities "execute outside the replay path and are automatically retried." Changing Activity Options is safe; changing the Activity type or ID is not. — [Temporal docs: Workflow Definition](https://docs.temporal.io/workflow-definition)
- Timers: durable; the Workflow suspends while a Timer runs. Changing a timer's duration is generally safe, except to/from 0 (Java/Python/Go) or -1 (.NET); reordering a Timer relative to an Activity is unsafe. — [Temporal docs: Workflow Definition](https://docs.temporal.io/workflow-definition)
- Event History hard limit: "limited to 51,200 Events or 50 MB"; warning "after 10,240 Events or 10 MB". — [Temporal docs: Workflow Execution limits](https://docs.temporal.io/workflow-execution/limits)
- Continue-As-New: "a mechanism by which the latest relevant state is passed to a new Workflow Execution" with a fresh Event History; needed because a long history may "bog down and have performance issues" or exceed limits, and because a Workflow started on older code "can hit versioning problems when it runs on newer code." Same Workflow Id, new Run Id. Can be repeated indefinitely ("Entity Workflows"). Server emits "Continue-As-New Suggested". Periodic Continue-As-New "keeps Workflows from running stale code." — [Temporal docs: Continue-As-New](https://docs.temporal.io/workflow-execution/continue-as-new)
- Message passing: "Signals are asynchronous write requests" (fire-and-forget, sender cannot await a response); "Queries are read requests" that cannot block and never add history; "Updates are synchronous, tracked write requests" that can be validated before being accepted into history. — [Temporal docs: Workflow message passing](https://docs.temporal.io/encyclopedia/workflow-message-passing)
- Human-gate pattern (Python): `await workflow.wait_condition(lambda: self.approved_for_release)` with a Signal handler setting the flag; `wait_condition` "prevent[s] the code from proceeding until a condition is true" and "you can optionally set a timeout"; it is "common to use" a wait condition "to wait for a particular Signal or Update to be sent by a Client." Update validators are optional, synchronous, and rejecting one means "`WorkflowExecutionUpdateAccepted` _won't_ be added to the Event History." — [Temporal docs: Python message passing](https://docs.temporal.io/develop/python/message-passing)
- Versioning (Python): patching is a three-step process: (1) `workflow.patched("my-patch")` branches between old and new logic and inserts a marker in history; (2) after no pre-patch executions remain, `workflow.deprecate_patch("my-patch")`; (3) once pre-patch workflows leave retention, remove both. If a Worker finds a patch marker in history the code doesn't produce, "it will fail the Workflow task." Worker Versioning tags Workers into Deployment Versions so "old Workers can run old code paths and new Workers can run new code paths." — [Temporal docs: Python versioning](https://docs.temporal.io/develop/python/versioning)
- AI guidance (vendor, 2025-07-10, Cornelia Davis): chains/graphs/agentic loops are "a Temporal Workflow"; LLM calls go through Activities for retries; tools and MCP clients run in Activities, MCP servers are Workflows+Activities; memory is "variables in your Workflow code" and durable; "You never have to think about checkpointing"; human-in-the-loop uses Signals, Updates and Queries; Workers cache active Workflows and replay Event History to rebuild evicted ones. The post does not discuss LLM non-determinism vs workflow determinism nor continue-as-new; it ends with a Temporal Cloud credit offer. — [Temporal blog: Durable Execution meets AI](https://temporal.io/blog/durable-execution-meets-ai-why-temporal-is-the-perfect-foundation-for-ai)
- OpenAI Agents SDK integration: announced 2025-07-30 (public preview, Python SDK); a later Temporal post says it reached GA on 2026-03-23. Positioned as adding retries and state persistence to agents "without rebuilding their architecture", preserving the SDK's model-agnostic design. — search snippets citing [Temporal blog: announcing OpenAI Agents SDK integration](https://temporal.io/blog/announcing-openai-agents-sdk-integration) and [BusinessWire 2025-07-30](https://www.businesswire.com/news/home/20250730783559/en/Temporal-and-OpenAI-Launch-Integration-for-Enterprises-Developing-Production-Agents) (UNVERIFIED: post bodies not opened).
- Funding context: a Temporal post dated 2026-09-14 announces a $550M Series E at $12.55B valuation framing durable execution as "a core requirement for modern AI systems." — search snippet for [temporal.io/blog](https://temporal.io/blog/temporal-raises-usd550m-series-e-at-usd12-55b-valuation-ai) (UNVERIFIED: not opened). A third-party roundup also mentions a $300M raise in Feb 2026 (UNVERIFIED, not opened; conflicting with/preceding the Sept figure).
- Third-party claim that Temporal "expanded its native AI agent SDK throughout 2025 and 2026" — [noqta.tn comparison](https://www.noqta.tn/blog/durable-execution-ai-agents-inngest-trigger-temporal-2026) (UNVERIFIED: not opened, non-official).

### Inferences
- Because the whole agent loop lives in the workflow function, every LLM result enters the history as an Activity result; the orchestrator then branches on it. That is legal (the branch is deterministic given the recorded result), so LLM non-determinism is absorbed at the Activity boundary. The constraint bites only if the *control-flow code itself* changes between replays.
- A multi-day pause is cheap in Temporal (timer or `wait_condition` with no timeout), but a long-lived agent conversation accumulates history toward the 51,200-event cap and must periodically `Continue-As-New`, which is also Temporal's own suggested answer to "workflow is running stale code."
- Editing the loop definition between passes is the hardest case for Temporal: it is exactly the "reordered/added/removed Command" scenario that triggers a non-deterministic error, and the sanctioned fixes (patch markers, Worker Versioning, Continue-As-New at a deploy boundary) all assume the change is a code deployment, not an edit to a prose template.

## Key Question 2: Inngest (step functions, `step.waitForEvent`, AgentKit)

### Takeaway
Inngest memoizes step results keyed by step ID and re-invokes (or, in TS SDK v4, checkpoints) the handler; code outside steps re-runs. `step.waitForEvent` and `step.sleep` suspend without a resident process (sleep up to 1 year; whole run bounded by plan: 30/90/366 days). Versioning is tolerant-by-ID rather than history-strict: same-ID steps reuse results, new steps run when reached, reorders only warn. AgentKit builds agent/network/router abstractions on top and uses `waitForEvent` inside a tool for human-in-the-loop.

### Cited Findings
- Execution model: "each step runs in a separate request to your app" under standard orchestration; with checkpointing (default in TS SDK v4) steps run back to back in one handler. Resume works by "returning saved step results, so completed work does not run again." Memoization: SDK hashes the step ID into a state key and skips the callback on replay. "Code outside a step can run again each time the handler replays." Non-deterministic work (DB/API) must go inside `step.run()`. Side effects must be idempotent because "a refund can succeed before its step result is saved, so the step may run again." Run state stored outside the function; self-hosting uses SQLite or Postgres. — [Inngest docs: How functions are executed](https://www.inngest.com/docs/learn/how-functions-are-executed)
- `step.waitForEvent`: "Inngest resumes the run with the event without keeping your function process running while it waits." `timeout` example `"7d"`; returns `null` on timeout; "Always handle the timeout, for example by recording an expired request or sending a reminder." "The wait only sees events sent after it starts listening." — [Inngest docs: wait-for-event](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/wait-for-event)
- Limits: `step.sleep()` / `step.sleepUntil()` "Up to 1 year" but within plan max run length; 1,000 steps per function; step timeout up to 2 hours; 4 MiB per step return; 32 MiB total run state; max function run length including sleeps: Free 30 days, Pro 90 days, Business 366 days, Enterprise custom. — [Inngest docs: usage limits](https://www.inngest.com/docs/usage-limits/inngest)
- Versioning of in-flight runs: saved results are reused for any step whose ID still matches; "New steps are executed when discovered, and if step execution order changes, the SDK logs a warning rather than failing the function"; a changed step ID is treated as a new step and runs again ("can repeat a payment, email, or resource creation"); "Changing step logic with the same ID is safe"; removed steps' data "remains in state but is simply ignored"; for rewrites that cannot use in-progress state, "create a function with a new ID. Keep the original function deployed until its runs finish." Recommended test: pause with `step.sleep()`, change code, resume. — search snippets from [Inngest docs: Versioning and Function Evolution](https://www.inngest.com/docs/learn/versioning) (page body partially seen via snippet; treat exact wording as near-verbatim but UNVERIFIED in full).
- AgentKit: "a framework to build AI Agents, from single model inference calls to multi-agent systems that use tools"; agents grouped into networks with a router choosing the next agent; shared "network state" as memory; MCP tool support; integrations with E2B, Browserbase, Smithery, Daytona; live traces via the Inngest Dev Server. The overview does not describe how steps provide durability. — [AgentKit overview](https://agentkit.inngest.com/)
- AgentKit human-in-the-loop: a tool handler calls `step.waitForEvent("developer.response", { event: "app/support.ticket.developer-response", timeout: "4h", match: "data.ticketId" })`, "pausing the execution of the AgentKit network"; the network must be wrapped in an Inngest function or the tool errors "This tool requires step context". — [AgentKit: Human in the loop](https://agentkit.inngest.com/advanced-patterns/human-in-the-loop)

### Inferences
- Inngest's ID-keyed memoization is the most forgiving of the replay engines for mid-run edits: adding a pass or editing the body of an already-completed pass does not break the run, which is closer to how a hand-edited template behaves. The price is that a renamed step silently re-executes.
- The plan-bound maximum run length (30 days on Free) is the operative limit for a loop that pauses for days between passes; Temporal and Cloudflare do not impose a comparable wall-clock cap on the whole run.
- AgentKit's HITL is a tool-level wait, so the "human gate" is modelled as a tool the agent chose to call, not a structural pause between passes.

## Key Question 3: Restate (durable promises, virtual objects)

### Takeaway
Restate journals every SDK operation in a replicated log (single Rust binary, optionally a consensus cluster); replay skips completed steps and `ctx.run` is the escape hatch for non-determinism. Waiting on humans is a first-class durable promise (awakeable / signal / workflow promise) with no hard sleep limit "for months or even years". Versioning is by immutable deployments: in-flight invocations are pinned to the old endpoint, and Restate explicitly advises against handlers that run for days or months because old deployments must stay alive until drained.

### Cited Findings
- Execution model: "Restate tracks every step of your code execution in a **journal**"; "Restate replays the journal, skipping completed steps"; "Each step is recorded in the journal and won't repeat on retry"; `run` actions retried with exponential backoff. Virtual Objects: "Each Virtual Object and Workflow execution has its own isolated state"; "Only one handler can modify state at a time, preventing race conditions"; "State updates are recorded alongside execution steps for consistency." Operations: the server is "a single binary written in Rust", run "as a high-availability cluster or as a single-node instance"; clusters "rely on a consensus algorithm to accept new entries in the log." — [Restate docs: Durable Execution](https://docs.restate.dev/concepts/durable_execution)
- Durable promises: Awakeable is "A convenient shorthand for a one-shot signal" with a generated ID an external system resolves or rejects (task-token style); Workflow promise is "A named value scoped to a workflow key", resolved once, retrievable by all handlers during retention; Signal is a durable notification by invocation ID and name, resolvable multiple times, e.g. `await ctx.signal<boolean>("approval")`. `ctx.run` wraps non-deterministic work because otherwise "these operations would produce different results during replay, breaking deterministic recovery." Sleep: "Handlers consume no resources while sleeping and resume at exactly the right time, even across restarts." — [Restate docs: Actions](https://docs.restate.dev/foundations/actions)
- Timers: "There is no hard limit on how long you can sleep. You can sleep for months or even years." On FaaS "Restate suspends the handler while it is sleeping, to free up resources." You "need to keep the deployment version until the invocation completes." Sleeping in an exclusive Virtual Object handler queues all other calls to that object. Clock skew between SDK and server can fire timers early/late. — [Restate docs: Durable timers (TS)](https://docs.restate.dev/develop/ts/durable-timers)
- Versioning: "When you deploy a version of your code, you give it an immutable, unique endpoint and register it with Restate"; retries go "always to the same endpoint"; "Existing requests continue on the original deployment." Avoid "long-running handlers (days or months)"; split with delayed calls. Virtual Object state "persists across versions" so schemas must stay backward compatible. Editing deployed code in place can cause journal mismatch (error RT0016); reordering/adding/removing SDK operations is unsafe; "Fixing a bug inside `ctx.run` is generally safe." Fix for in-flight invocations: register fixed deployment, pause affected invocations, resume on new deployment; the fix "must match the already-recorded journal entries." — [Restate docs: Versioning](https://docs.restate.dev/operate/versioning)

### Inferences
- Restate's explicit "avoid handlers that run for days or months" is in tension with a loop that idles for days between passes; its own recommended shape is a chain of short handlers linked by delayed calls, with state in a Virtual Object. That is structurally a state machine over an object, not a single long function.
- Virtual Objects (keyed state + serialized handlers) are the closest Restate analogue to "one document is the state": one object per loop, each pass a handler invocation.

### Gaps
- Exact awakeable creation/resolution API and timeout semantics were not on the pages opened.
- No Restate-specific AI agent SDK page was opened; the ZenML post groups Restate with Temporal as imposing determinism constraints (see KQ10).

## Key Question 4: DBOS (Postgres-backed durable execution, "durable AI agents")

### Takeaway
DBOS is a library (Python/TS) that checkpoints workflow inputs and step outputs into a Postgres "system database" with no separate server; recovery re-invokes the workflow with checkpointed inputs and returns checkpointed step results. Human waits use `DBOS.recv`/`DBOS.send` (durable messages) and `set_event`/`get_event` (status), surviving restarts "hours or days." Workflow functions must be deterministic; breaking changes are "any change in what steps run or the order in which steps run," handled by patching or app versioning so workflows "only recover to processes running compatible code."

### Cited Findings
- Architecture: "There's no separate orchestration server and no infrastructure required besides Postgres." "Every workflow input and step output is durably stored in the system database." "If there is a checkpoint, the step returns the checkpointed output instead of executing"; "once a step completes and is checkpointed, it is never re-executed." "DBOS restarts each interrupted workflow by calling it with its checkpointed inputs." "The workflow function must be deterministic"; non-deterministic work "you should do it in a step instead." "Steps should be idempotent." Versioning: two strategies (patching, versioning); a breaking change is "any change in what steps run or the order in which steps run"; "DBOS versions applications and workflows so workflows only recover to processes running compatible code." Conductor (separate control plane for recovery coordination/dashboards) is recommended, not required, and is "off your workflows orchestration path." Throughput rule of thumb: "each Postgres vCPU can process about 1,000 workflows or steps per second"; large outputs should go to blob storage with steps returning pointers. — [DBOS docs: Architecture](https://docs.dbos.dev/architecture)
- Human-in-the-loop: `approval = DBOS.recv(timeout_seconds=TIMEOUT)`; the workflow can "safely wait for a long time" and "will recover and keep waiting" across restarts and upgrades; a human "might take hours or days to respond"; `DBOS.send(agent_id, response)` from an HTTP endpoint, after which "the destination workflow is guaranteed to receive it"; status published via `DBOS.set_event` / read via `DBOS.get_event`; list agents awaiting input with `DBOS.list_workflows_async(status="PENDING", name=...)` then filter on a `"pending_approval"` event; example treats timeout as denial. — [DBOS docs: Human-in-the-loop](https://docs.dbos.dev/ai/hitl)
- Agent rationale (vendor, 2025-02-24, Qian Li): "the missing piece is durable execution for AI agents"; LangChain/LlamaIndex "don't simply handle long-running human input, retries, parallelism, or crashes"; demo wraps LangGraph tools as `@DBOS.workflow()` with `@DBOS.step`/`@DBOS.transaction`; approval workflow emails a manager then "pauses and waits for a notification" via `DBOS.recv`, resumed by an HTTP endpoint calling `DBOS.send`. The post does not say the LLM invocation node is itself a DBOS step and does not address LLM non-determinism vs replay. — [DBOS blog: Durable Execution for Building Crashproof AI Agents](https://dbos.dev/blog/durable-execution-crashproof-ai-agents)
- Integrations listed: Pydantic AI, LlamaIndex, OpenAI Agents SDK, Google ADK; the ADK plugin "can pause execution and resume it later after receiving an external signal or human approval." — search snippets ([DBOS Pydantic AI integration](https://docs.dbos.dev/integrations/pydantic-ai), [ADK DBOS plugin](https://adk.dev/integrations/dbos/)) (UNVERIFIED: not opened).

### Inferences
- DBOS's "Postgres is the only infrastructure" is the lowest operational floor among server-backed engines; for a single operator it is one database. But the determinism/versioning contract is the same as Temporal's in substance: change the step sequence and in-flight runs must be pinned to old code.
- `list_workflows(status="PENDING")` + events is the DBOS answer to "which loops are waiting on me" — the equivalent of grepping markdown files for an unfilled gate line.

- `/explanations/why-dbos-agents` returned empty content; DBOS's dedicated "why agents" argument is taken from the Feb 2025 blog instead.
- Maximum `recv` timeout and durable-sleep ceilings not stated on pages opened.

## Key Question 5: Vercel Workflow / Workflow DevKit ("use workflow" / "use step")

### Takeaway
Vercel Workflows (GA 2026-04-16) compiles `"use workflow"` functions into an orchestrator route that is re-run against an event log, with `"use step"` functions compiled into isolated routes; the workflow sandbox pins `Math.random`/`Date` so replays are deterministic and has no Node runtime. Sleep and hooks suspend "minutes to months" without compute; hooks (`defineHook`/`.create`/`.resume`) are the human-gate. Runs are pinned to the deployment that started them ("Skew Protection"); moving a run to new code means cancel-and-rerun or chaining bounded runs with `deploymentId: "latest"`. `WorkflowAgent` (AI SDK) runs the agent loop inside a workflow with tools as steps.

### Cited Findings
- Model: "Vercel Workflows runs multi-step logic as durable code that can retry failed steps, wait for external events, and resume across crashes and deployments." Built on the open-source Workflow SDK (JS/TS) and the `vercel` Python SDK. Vercel Functions execute code; Vercel Queues enqueue; "Managed persistence stores all state and event logs." "Resumable: Pause for minutes or months"; "Durable: Survive deployments and crashes with deterministic replays." "Every step, input, output, sleep, and error inside a workflow is recorded automatically." Multi-region: a run is pinned to one region for its lifetime (requires `workflow` 5.0.0-beta.33+). Also lists `durable-harness` for Pi, Claude Code, Codex, OpenCode "so sessions can resume after crashes and deployments", and eve, which "uses Workflows for durable sessions and adds built-in channels and approvals." Page last updated 2026-09-04. — [Vercel docs: Workflows](https://vercel.com/docs/workflow)
- Concepts (last updated 2026-09-10): four abstractions: Workflow (stateful, "remembers its progress and can resume exactly where it left off, even after pausing, restarting, or deploying new code"), Step ("stateless function that runs a unit of durable work", built-in retries, "compiles into an isolated API route"; "While the step executes, the workflow suspends without consuming resources"), Sleep (`await sleep('7 days')`, "consume no resources"), Hook ("lets a workflow wait for external events such as user actions, webhooks, or third-party API responses... human-in-the-loop workflows"). Example: `approvalHook.create({ token: 'draft-123' })` then `for await (const event of events)`; an API route calls `approvalHook.resume('draft-123', {...})`. "All inputs and outputs are recorded in an event log. If a deploy or crash happens, the system replays execution deterministically from where it stopped." Skew Protection: "Workflows keep running on the deployment they were created on"; a rollback "does not stop runs on the deployment you rolled back from"; runs pinned to a deleted deployment "never complete or fail on their own, so cancel them as well." Human review guidance: authenticate the reviewer, "Confirm that the request still matches the version they reviewed, and record the approval separately from execution." — [Vercel docs: Workflow Concepts](https://vercel.com/docs/workflows/concepts)
- Workflow SDK foundations: workflow functions "define the entrypoint of a workflow and organize how step functions are called" and do "not have access to the Node.js runtime, and usable `npm` packages are limited"; step functions "perform the actual work in a workflow and have full runtime access", default "maximum of 3 retry attempts"; "All step results are persisted to the event log"; "the workflow code gets re-run multiple times during its lifecycle"; "Must be **deterministic** to allow resuming after failures"; the sandbox fixes `Math.random` and `Date` so "the values don't change across replays" (so generate secrets inside a step); parameters pass "by **value, not by reference**"; webhooks via `createWebhook()` resume "when an external system passes data into the workflow." — [Workflow SDK: Workflows and Steps](https://workflow-sdk.dev/docs/foundations/workflows-and-steps)
- Versioning: "Workflow runs are pinned to the deployment that starts them" including while sleeping, waiting on a hook, or retrying. To fix in-flight runs: deploy the fix, find affected runs, cancel, rerun with same inputs ("Rerun on latest"); or `start()` with `deploymentId: "latest"` (Vercel-specific, may be renamed `version`), requiring workflow name, file path, arguments and return value to stay backward-compatible. "For long-running workflows, the doc suggests chaining bounded runs" where "the serialized state is the migration boundary between versions." Mismatched code "can break long-running work in hard-to-debug ways." — [Workflow SDK: Versioning](https://workflow-sdk.dev/docs/foundations/versioning)
- AI: `WorkflowAgent` from `@ai-sdk/workflow` "runs the agent loop inside a workflow" and persists state across step boundaries; tools become durable by adding `"use step"`; failed tool calls retried "up to 3 times by default"; a step "may execute it inline in the flow request or resume it through the workflow queue"; approvals and resumable streams are linked, not detailed. — [Workflow SDK: AI](https://workflow-sdk.dev/docs/ai)
- GA post (2026-04-16): problem statement: "Code that's trivial to run locally falls apart the moment it needs to handle failures, restarts, and real traffic"; the event log "records every step input, output, stream chunk, sleep, hook, and error in a run" and is "the single source of truth for execution state and history"; Workflows 5 adds "A snapshot-based runtime to reduce replay overhead as event histories grow"; "Workflow SDK is open source"; Worlds = adapters providing event log, compute, queue: Managed, Self-hosted ("We maintain a Postgres reference implementation"), Embedded, plus community Worlds (MongoDB, Redis, Turso, Jazz Cloud, Cloudflare); agents are a primary use case ("infinitely long running durable agents", `DurableAgent`, `WorkflowAgent` in AI SDK v7); durable streams let clients "disconnect from, reconnect to later, and resume from any point"; coding agents get `npx workflow inspect runs` and an installable skill. — [Vercel blog: A new programming model for durable execution](https://vercel.com/blog/a-new-programming-model-for-durable-execution)

### Inferences
- Vercel's "pin to deployment" is the bluntest versioning policy: there is no patch-marker mechanism; the engine's answer to "the definition changed mid-run" is "finish on the old code, or cancel and restart from inputs." For a loop whose template is edited between passes, this means each pass would effectively be its own run (which the docs themselves recommend as "chaining bounded runs").
- Vercel is unusual in explicitly targeting coding-agent harnesses (`durable-harness` for Claude Code etc.) — the closest any vendor comes to the user's "Claude Code loop" setting, but what it persists is the *session*, not a human-edited document.

## Key Question 6: Cloudflare Workflows / Agents SDK (Durable Objects)

### Takeaway
Cloudflare Workflows persists `step.do` return values (<=1 MiB each), supports `step.sleep` up to 365 days and `step.waitForEvent` (default 24h timeout; event waits "up to 1 year"), with 10,000-25,000 steps per instance on Paid and 1 GB state. The Agents SDK makes each agent a Durable Object ("a durable identity, local SQL storage, real-time connections, scheduled work, and recoverable execution") and delegates long waits to Workflows via `waitForApproval()`, "backed by Cloudflare Workflows, so the wait can continue for months or longer without keeping an Agent running."

### Cited Findings
- Workers API: `step.do` persists a named callback's return value (name <= 256 chars); `step.sleep` / `step.sleepUntil`; `step.waitForEvent` "The default timeout is 24 hours"; retries per step (`limit`, `delay`, `backoff`, `timeout`); `NonRetryableError` "stops step retries, propagating the error to the top level"; step return values must be structured-cloneable and "no longer than 1 MB" (streams allowed for larger binary output); Paid "10,000 steps by default" up to 25,000, Free 1,024; sleeps do not count toward the step limit; rollbacks run in reverse step-start order on failure. ### Inferences
- Cloudflare splits the two concerns the user's loop conflates: the Durable Object holds live state (SQL) and identity; the Workflow holds the long pause. The "document" would be the DO's SQL row; the "gate line" would be `waitForApproval` + `approveWorkflow()`.
- 1 MiB per step output is a real constraint if step outputs are whole markdown documents or transcripts; the pattern would be to store the document elsewhere and pass a reference.

## Key Question 7: Data orchestrators (Airflow, Prefect, Dagster) — fit for agent loops

### Takeaway
All three now have a human-pause primitive (Airflow 3.1's `ApprovalOperator`/`HITLOperator` family, Prefect's `pause_flow_run(wait_for_input=...)`), so the "cannot wait for a human" objection is dated. The remaining mismatch, as argued by ZenML (2026-03-12), is that DAG orchestrators "assume you know the shape of execution before it starts" and treat dynamic branching as "patches on a model that fundamentally assumes static structure"; Dagster is asset-centric and has no stated agent-durability position that I could find.

### Cited Findings
- Airflow 3.1 added `HITLOperator` (base), `ApprovalOperator` (approve/reject), `HITLBranchOperator`, `HITLEntryOperator` in the standard provider (`airflow.providers.standard.operators.hitl`); each creates a pending action under Browse -> Required Actions or via REST; while waiting "human-in-the-loop operators don't take up a worker slot" (deferrable in 3.1/3.2; in 3.3+ they enter an `awaiting_input` task state needing no triggerer or worker). — search snippets from [Astronomer: Human-in-the-loop workflows with Airflow](https://www.astronomer.io/docs/learn/airflow-human-in-the-loop) and [Airflow 3.3.2 HITL tutorial](https://airflow.apache.org/docs/apache-airflow/3.3.2/tutorial/hitl.html) (UNVERIFIED: pages not opened).
- Prefect: `pause_flow_run` / `suspend_flow_run` accept `wait_for_input` (built-in type, `pydantic.BaseModel`, or `RunInput`); resume via `resume_flow_run(flow_run_id, run_input={...})` or the UI form; validation failure fails the run (docs suggest a loop that pauses again). Prefect's 2024 HITL blog uses older syntax; no official Prefect agent-loop example found. — search snippets from [Prefect docs: Interactive workflows](https://docs.prefect.io/v3/advanced/interactive.md) and [Prefect blog: HITL workflows](https://www.prefect.io/blog/human-in-the-loop-workflows) (UNVERIFIED: not opened).
- ZenML (2026-03-12, Hamza Tahir): Airflow is the "canonical tool" of Era 1 batch scheduling; DAG orchestrators (Prefect, Dagster, Kubeflow, ZenML, Argo) "assume you know the shape of execution before it starts" and their escape hatches are "patches on a model that fundamentally assumes static structure"; Era 2 ML pipelines didn't need "human-in-the-loop, pause and resume" because "the graph was still known at compile time"; durable execution (Temporal, Restate) "handles the control part but imposes determinism constraints that fight the inherently non-deterministic nature of LLM-based systems." — [ZenML blog: From Pipelines to Agents](https://www.zenml.io/blog/from-pipelines-to-agents)
- Third-party characterisations: Prefect's "dynamic Python flows make the control flow itself the graph"; Airflow suits teams that "pre-orchestrate a multi-step sequence as an Airflow DAG that the agent triggers"; Dagster "treats the data assets produced by your AI agents as first-class citizens"; none of the three validates agent output. — search snippets ([Kinde guide](https://kinde.com/learn/ai-for-software-engineering/ai-devops/orchestrating-multi-step-agents-temporal-dagster-langgraph-patterns-for-long-running-work/), [agentpedia roundup](https://agentpedia.codes/blog/ai-ml-orchestration-tools-2026)) (UNVERIFIED, secondary).

### Inferences
- Data orchestrators model a run as a scheduled instance of a pre-declared graph with a scheduler + metadata DB (+ triggerer/workers for Airflow). For a loop with a handful of passes and a human gate, Airflow 3.3's `awaiting_input` state is functionally a durable wait; what it lacks is memoized replay of a dynamic, LLM-driven control flow — the next pass cannot be decided by the previous pass's output without dynamic-task-mapping escape hatches.
- Their advantage over durable-execution engines for the user is the opposite of what matters here: a UI and audit trail for *many* scheduled runs. For one operator and one loop they are the heaviest option (scheduler, metadata DB, web server, workers).

## Key Question 9: Cross-cutting — determinism vs model calls; versioning mid-run; the human-approval primitive; observability

### Takeaway
Every replay engine resolves LLM non-determinism the same way: the model call is a journaled step, so replay returns the recorded output and the orchestrator's branching on it is deterministic by construction; the constraint is on the orchestrator code, not the model. Versioning policies form a spectrum from strict (Temporal/Restate/DBOS: history mismatch is an error; patch markers or pinned deployments) through forgiving (Inngest: ID-keyed, reorder only warns) to pin-and-rerun (Vercel). The human gate is universally "suspend until a named external message arrives, with an optional timeout measured in days-to-years." Observability is a per-run timeline of recorded step inputs/outputs.

### Cited Findings
- Determinism, as each engine states it: Temporal — LLM invocations "belong in Activities"; mismatch yields "a _non-deterministic_ error" ([Temporal](https://docs.temporal.io/workflow-definition)). DBOS — "The workflow function must be deterministic"; non-deterministic work in a step ([DBOS](https://docs.dbos.dev/architecture)). Restate — without `run`, operations "would produce different results during replay, breaking deterministic recovery" ([Restate](https://docs.restate.dev/foundations/actions)). Vercel — workflow functions "Must be **deterministic**"; sandbox pins `Math.random`/`Date` ([Workflow SDK](https://workflow-sdk.dev/docs/foundations/workflows-and-steps)). Inngest — "Code outside a step can run again each time the handler replays" ([Inngest](https://www.inngest.com/docs/learn/how-functions-are-executed)). Cloudflare Code Mode — approval "reruns the same source and execution ID, replaying completed calls from the durable log" ([Cloudflare HITL](https://developers.cloudflare.com/agents/concepts/agentic-patterns/human-in-the-loop/)).
- Critic view: durable execution "imposes determinism constraints that fight the inherently non-deterministic nature of LLM-based systems" — [ZenML 2026-03-12](https://www.zenml.io/blog/from-pipelines-to-agents). Search-summarised critique: replay engines "impose constraints on how orchestration code is written, and a second mechanism — idempotency keys — that you still have to supply yourself for anything that mutates the outside world." — search snippet (source not individually opened; UNVERIFIED attribution).
- Versioning policies: Temporal patch lifecycle and Worker Versioning ([Temporal Python versioning](https://docs.temporal.io/develop/python/versioning)); Continue-As-New as the deploy-boundary reset ([Temporal CAN](https://docs.temporal.io/workflow-execution/continue-as-new)); Restate immutable endpoints, "Existing requests continue on the original deployment", in-place edits risk RT0016 ([Restate versioning](https://docs.restate.dev/operate/versioning)); DBOS breaking change = "any change in what steps run or the order in which steps run" ([DBOS](https://docs.dbos.dev/architecture)); Inngest "if step execution order changes, the SDK logs a warning rather than failing the function" ([Inngest versioning](https://www.inngest.com/docs/learn/versioning), snippet); Vercel runs "pinned to the deployment that starts them", fix by cancel + "Rerun on latest" or `deploymentId: "latest"` ([Workflow SDK versioning](https://workflow-sdk.dev/docs/foundations/versioning)).
- Human-approval primitives and their stated horizons: Temporal `wait_condition` on a Signal/Update, optional timeout ([Temporal](https://docs.temporal.io/develop/python/message-passing)); Inngest `step.waitForEvent` with `"7d"`-style timeout, run length <= 30/90/366 days by plan ([Inngest](https://www.inngest.com/docs/features/inngest-functions/steps-workflows/wait-for-event), [limits](https://www.inngest.com/docs/usage-limits/inngest)); Restate awakeable/signal/workflow promise, sleep "months or even years" ([Restate actions](https://docs.restate.dev/foundations/actions), [timers](https://docs.restate.dev/develop/ts/durable-timers)); DBOS `recv(timeout_seconds=...)`, "hours or days" ([DBOS HITL](https://docs.dbos.dev/ai/hitl)); Vercel hooks `create`/`resume`, "minutes or months" ([Vercel concepts](https://vercel.com/docs/workflows/concepts)); Cloudflare `waitForEvent` default 24 h, `waitForApproval` "months or years", sleep <= 365 days ([Cloudflare run-workflows](https://developers.cloudflare.com/agents/api-reference/run-workflows/), [limits](https://developers.cloudflare.com/workflows/reference/limits/)); Trigger.dev waitpoint token with optional no-timeout ([Trigger.dev](https://trigger.dev/docs/wait-for-token)); Airflow 3.1+ `ApprovalOperator` / `awaiting_input` (UNVERIFIED snippet).
- Observability as stated: Temporal replays Event History to rebuild evicted workflows (vendor blog); DBOS `list_workflows(status="PENDING")` + `get_event` ([DBOS HITL](https://docs.dbos.dev/ai/hitl)); Vercel "Every step, input, output, sleep, and error inside a workflow is recorded automatically", dashboard + `npx workflow inspect runs`, run data readable by owners / "Workflow Run Data Viewer" role ([Vercel docs](https://vercel.com/docs/workflow)); Cloudflare waiting runs show status "waiting" ([Cloudflare](https://developers.cloudflare.com/agents/api-reference/run-workflows/)); Hatchet "replay failed runs with a single click" ([Hatchet](https://hatchet.run/use-cases/ai-agents)); Inngest Dev Server "local live traces and input/output logs" ([AgentKit](https://agentkit.inngest.com/)).
- Vercel's own human-review guidance adds a governance layer the engines don't provide: "Confirm that the request still matches the version they reviewed, and record the approval separately from execution." — [Vercel concepts](https://vercel.com/docs/workflows/concepts)

### Inferences
- "Determinism" in these engines is a property of the *orchestrator code between step calls*, never of the model. The LLM is always allowed to be random because its output is recorded once. The user's concern ("LLM calls are non-deterministic") is therefore not a blocker; the real constraint is that the *sequence of step calls* must be reproducible from recorded outputs — which is exactly what an edited template breaks.
- The engines differ most in what they do when the definition changes under a sleeping run. For a loop whose template is edited between passes, only Inngest's ID-keyed policy and Vercel's "bounded runs chained with state as the migration boundary" are tolerant without ceremony; Temporal/Restate/DBOS require explicit patch/version handling.

### Gaps
- No engine page opened offers a quantitative comparison of replay overhead for long histories; Vercel mentions a snapshot runtime, Temporal a 51,200-event cap, Inngest a 1,000-step cap; others unstated.

## Key Question 10: Published opinions — "do agents need durable execution?" and the files + git counter-argument

### Takeaway
Vendor and vendor-adjacent writing (Temporal, DBOS, ZenML, Diagrid, Dapr maintainers in the Microsoft Agent Framework thread) argue durable execution is necessary once runs are long, expensive to repeat, distributed, or paused on humans; the strongest published counter-argument (Cidre, 2026-05-15) is that for one host, minutes-scale steps and one or two observers, "files plus git" already gives resume-by-default and an audit trail, and an engine is warranted only "when you can name the specific durability problem it solves for you."

### Cited Findings
- "There Is No Workflow Engine. It's Just Git." (2026-05-15, Adrià Cidre): overnight agent pipeline with "no workflow engine, database, or queue"; a plan file lists tasks with `todo`/`done` status; one markdown file per bug with frontmatter status; the orchestrator "walks to the first task that isn't done"; each fix is a commit with a `Bug: <id>` trailer; "There's no `state.json`, no SQLite database, no Redis queue." Ctrl+C: anything written "is kept"; "The worst case is one half-edited file in your working tree." Resume is default: "The next run reads the same files and continues." "The state file is the configuration." Limits the author names: "Files are local" (many agents across machines need locks/leases/queue); thousands of sub-second steps mean "you need a real engine"; fan-out/conditionals/joins push toward "reinventing a workflow DSL"; no dashboard ("You can't show a PM a green checkmark"); only `rm -rf` loses state. A separate completed-tasks log "caused a divergence bug, so status moved onto the task itself"; cron-driven retries "couldn't tell retryable failures from ones needing a human." When to add an engine: "the right time to add one is when you can name the specific durability problem it solves for you." — [adriacidre.com](https://adriacidre.com/blog/there-is-no-workflow-engine/)
- Related file-first patterns (search snippets, UNVERIFIED): "GitAgent" treats git as the state store with memory as markdown files and each event a commit ([Medium](https://medium.com/@shreyas.kapale/gitagent-all-ai-agents-should-follow-these-14-patterns-ffc0a79bac0e)); "Markdown Files as State Machines" reports checkpoint files recovering an agent after context compaction ([understandingdata.com](https://understandingdata.com/posts/markdown-files-as-state-machines/)); "The Case for Markdown as Your Agent's Task Format" ([dev.to](https://dev.to/battyterm/the-case-for-markdown-as-your-agents-task-format-6mp)); Microsoft Learn recommends "durable artifacts and consistent sources of truth" with GitHub as source of truth ([learn.microsoft.com](https://learn.microsoft.com/en-us/training/modules/memory-state-evaluation/4-memory-state-continuity)). Counterexample: a PR proposing a Temporal engine for an agent loop argues the prior LangGraph choice "was a description of a durable execution engine's product" ([github.com/imaustink/agent-controller/pull/194](https://github.com/imaustink/agent-controller/pull/194)).
- Microsoft Agent Framework discussion #1092 (opened 2025-10-01): Yaron Schneider (Dapr) 2025-10-02: "Checkpointing is expensive and unreliable compared to durable execution," citing an atomicity gap (crash after a step completes but before the checkpoint flushes) and multi-instance races; Dapr's append-only log commits "the activity and its record as a single commit." Eric Zhu conceded "Checkpointing does have issues... It is not perfect." Cecil Phillip 2025-10-03: "at scale, checkpointing isn't enough." georgestevens99 2025-10-07: checkpointing is a mechanism for durable execution, not a rival. Chris Gillum 2025-10-15: durable execution "worthwhile as another option," both graph-based and durable approaches should be supported. Outcome: a Durable Task extension for MAF merged (PR #1916) by 2025-11-14; 2025-11-17 Gillum: graph-based = declarative, durable orchestrations = imperative, "the choice depending on team preference." Petrus Pennanen 2026-02-25 proposed a lighter "receipt-log" and asked for benchmarks of Temporal-style durability vs simple checkpointing — "The thread contains no benchmarks." — [GitHub discussion](https://github.com/microsoft/agent-framework/discussions/1092)
- ZenML "Why Your AI Agents Need Durable Execution" (2026-03-01): "every failure means starting over from scratch"; proposes per-step checkpointing (Kitaru `@checkpoint`/`@flow`) enabling HITL pauses, replay with overrides, versioned artifacts; building it yourself is "infrastructure work, not agent work"; does not discuss determinism, operational cost, versioning, or files/git. — [ZenML blog](https://www.zenml.io/blog/why-agents-need-durable-execution)
- Workflow Builder (2026-07-21, Maciej Teska, vendor): durable execution "does not solve the whole product problem" — it covers surviving "a failed API call, a deployment, a rate limit or a delayed approval," but not authoring by non-engineers, product-facing visibility ("where approval happens or which rules apply"), or governed iteration of prompts/tools/routing; runtime dashboards exposed to customers create "a confused product surface." Concedes code-first is reasonable when only engineers configure the flow. — [workflowbuilder.io](https://www.workflowbuilder.io/blog/why-durable-execution-alone-wont-save-your-ai-agent)
- Search-summarised consensus (sources not individually opened, UNVERIFIED): "If it fails, run it again and you have lost five seconds and one model call"; durable execution "earns its cost only when a run is long enough to be interrupted, expensive enough that repeating it hurts, or paused on something outside your own process"; "Running a service like Temporal is also a real cost for a small team." — [frenchydigital 2026 guide](https://frenchydigital.com/blog/ai-agent-durable-execution-2026), [Quellix Labs](https://quellixlabs.com/insights/durable-execution-long-running-ai-agent-workflows).
- Diagrid FAQ (vendor): "checkpointing helps, but it is usually not enough by itself for production AI agents." — search snippet ([diagrid.io](https://www.diagrid.io/faq/durable-execution/where-does-workflow-orchestration-fit-in-an-ai-agent-architecture)) (UNVERIFIED).

### Inferences
- The two camps are not disagreeing about guarantees; they disagree about *who* must be resilient. The engine camp assumes many concurrent, unattended, distributed runs; the files camp assumes one operator who can read the state and re-run. Cidre's enumerated limits (locality, step granularity, branching, dashboard) are precisely the conditions absent from a single-operator, days-between-passes loop.
- The Schneider atomicity argument (crash between step completion and checkpoint flush) does apply to a markdown loop: a pass may complete its model call and crash before the document is written. The mitigation in the files camp is that the operator notices and re-runs the pass, paying one model call; the engine camp's mitigation is a single-commit log. Which is acceptable is a cost question, not a correctness one.

### Gaps
- No independent benchmark comparing engine-backed vs file-backed agent loops exists in anything opened; the MAF thread explicitly notes none.
- Most "do agents need it" posts are vendor-authored; I found no neutral academic or large-operator writeup.

## Key Question 11: What would stop this from managing something other than code-defined workflows

### Takeaway
Every engine surveyed requires the process definition to be executable code (or, for LittleHorse/Airflow, a declared spec/graph) that the engine can re-invoke; the "state" is an engine-owned log of serialized step outputs, not a human-editable artifact; and the contract around changing the definition assumes a deployment event. A prose template interpreted by an LLM, edited by hand between passes, violates all three assumptions.

### Cited Findings
- Definition must be code the engine re-executes: Temporal re-runs the workflow function and compares emitted Commands to history ([Temporal](https://docs.temporal.io/workflow-definition)); DBOS "restarts each interrupted workflow by calling it with its checkpointed inputs" ([DBOS](https://docs.dbos.dev/architecture)); Vercel "the workflow code gets re-run multiple times during its lifecycle" and runs in a sandbox with no Node runtime ([Workflow SDK](https://workflow-sdk.dev/docs/foundations/workflows-and-steps)); Inngest replays the handler and returns saved results ([Inngest](https://www.inngest.com/docs/learn/how-functions-are-executed)); Restate "replays the journal, skipping completed steps" ([Restate](https://docs.restate.dev/concepts/durable_execution)); Trigger.dev restores a CRIU process image ([Trigger.dev](https://trigger.dev/docs/how-it-works)). Vercel's "Dynamic workflows" (experimental) can "Start runs from workflow source assembled after deployment, over steps already deployed with your app" — still source code, still over pre-deployed steps ([Vercel docs](https://vercel.com/docs/workflow)).
- State is an engine-owned serialized log, with size/shape constraints: Temporal 51,200 events / 50 MB ([limits](https://docs.temporal.io/workflow-execution/limits)); Cloudflare 1 MB per step value, structured-cloneable only ([Workers API](https://developers.cloudflare.com/workflows/build/workers-api/)); Inngest 4 MiB per step, 32 MiB per run ([limits](https://www.inngest.com/docs/usage-limits/inngest)); DBOS write sizes "determined by the sizes of your inputs and outputs", large outputs to blob storage ([DBOS](https://docs.dbos.dev/architecture)); Vercel parameters "by **value, not by reference**", mutations inside a step not visible to the workflow ([Workflow SDK](https://workflow-sdk.dev/docs/foundations/workflows-and-steps)); LittleHorse's critique that durable-execution updates are "retry cache information, not business data" ([LittleHorse](https://littlehorse.io/compare/durable-execution)).
- Changing the definition is a deployment event with a compatibility contract: Temporal patch markers and Worker Versioning ([Temporal](https://docs.temporal.io/develop/python/versioning)); Restate "immutable, unique endpoint" per version, in-place edits break replay ([Restate](https://docs.restate.dev/operate/versioning)); DBOS breaking change = change in "what steps run or the order" ([DBOS](https://docs.dbos.dev/architecture)); Vercel runs "pinned to the deployment that starts them" ([Workflow SDK](https://workflow-sdk.dev/docs/foundations/versioning)); Inngest tolerant by step ID but renames re-execute ([Inngest versioning](https://www.inngest.com/docs/learn/versioning), snippet).
- The human gate is a typed message to a named wait, not an edit to the state: Temporal Signal/Update ([Temporal](https://docs.temporal.io/develop/python/message-passing)); Inngest event matched on `data.ticketId` ([AgentKit HITL](https://agentkit.inngest.com/advanced-patterns/human-in-the-loop)); DBOS `send(workflow_id, payload)` ([DBOS HITL](https://docs.dbos.dev/ai/hitl)); Vercel `approvalHook.resume(token, data)` ([Vercel concepts](https://vercel.com/docs/workflows/concepts)); Cloudflare `approveWorkflow()`/`rejectWorkflow()` ([Cloudflare](https://developers.cloudflare.com/agents/api-reference/run-workflows/)); Trigger.dev POST to the token URL ([Trigger.dev](https://trigger.dev/docs/wait-for-token)); Restate awakeable resolved by ID ([Restate actions](https://docs.restate.dev/foundations/actions)).
- Authoring/governance is explicitly out of scope for the engines, per critics: Workflow Builder — durable execution "does not solve the whole product problem" (authoring, visibility, governed iteration) ([workflowbuilder.io](https://www.workflowbuilder.io/blog/why-durable-execution-alone-wont-save-your-ai-agent)); LittleHorse — "No end-to-end business flow: only intermediate states and failures" ([LittleHorse](https://littlehorse.io/compare/durable-execution)).

### Inferences
- A loop whose "definition" is a prose template is, to these engines, a *step input*, not a workflow. The only way to host it is a fixed outer workflow (`for pass in passes: result = step(run_llm(template, doc)); await human_gate()`), where the template and document are opaque payloads. The engine would then guarantee the outer loop (pass counter, gate, timers) and nothing about the content.
- Editing the template between passes is harmless in that framing only because the engine never sees it — it is data. Editing the *outer loop* (number of passes, where the gate sits) is the breaking change every engine warns about.
- The engine's journal is not readable or editable by the owner as a document; the human cannot "write a line" into it. The gate has to be a message, so a document-edit-as-gate would need a watcher that converts a file change into a signal/event, which reintroduces a daemon.
- Payload limits (1 MB / 4 MiB per step) mean whole documents or transcripts cannot be the step outputs; they would live in files or blob storage with the engine holding pointers — at which point the files are the state and the engine is a pointer log.

### Gaps
- No engine documentation opened describes a supported mode where the process definition is non-code data interpreted at runtime, beyond Vercel's experimental "dynamic workflows" (still source over deployed steps).

## Key Question 12: Where this overlaps with, and differs from, a loop whose state is a markdown document edited by hand

### Takeaway
The overlap is the problem statement: both exist so that a multi-step process can pause for days, survive interruption, resume at the right point, and leave a record. The difference is where truth lives and who can edit it: in an engine, truth is an append-only, engine-owned log of step results keyed to a fixed code path, edited only through typed messages and deployments; in the markdown loop, truth is a mutable document the owner and the model both read and write, the "definition" is prose re-interpreted each pass, and the gate is a line in that document.

### Cited Findings
- Shared goals, in vendors' words: "retry failed steps, wait for external events, and resume across crashes and deployments" ([Vercel](https://vercel.com/docs/workflow)); "Pause for minutes or months, then resume from the exact point" ([Vercel](https://vercel.com/docs/workflow)); "wait hours or days for a notification" ([DBOS HITL](https://docs.dbos.dev/ai/hitl)); "the wait can continue for months or longer without keeping an Agent running" ([Cloudflare HITL](https://developers.cloudflare.com/agents/concepts/agentic-patterns/human-in-the-loop/)); "You never have to think about checkpointing" ([Temporal blog](https://temporal.io/blog/durable-execution-meets-ai-why-temporal-is-the-perfect-foundation-for-ai)).
- The file-based equivalent of each guarantee, from the one published file-first account: resume = "skips anything marked `done`"; crash = "anything already written is kept... worst case is one half-edited file"; control = "The state file is the configuration"; audit = commits with `Bug: <id>` trailer; observability = `cat`, `git log`, `ls`; stated limits = locality, step granularity, branching, no dashboard ([Cidre 2026-05-15](https://adriacidre.com/blog/there-is-no-workflow-engine/)).
- Engine-side properties with no file analogue: exactly-once step memoization ("once a step completes and is checkpointed, it is never re-executed" — [DBOS](https://docs.dbos.dev/architecture)); atomic step+record commit (Schneider: checkpointing "has an atomicity gap" — [MAF #1092](https://github.com/microsoft/agent-framework/discussions/1092)); serialized access per key ("Only one handler can modify state at a time" — [Restate](https://docs.restate.dev/concepts/durable_execution)); durable timers that fire without a resident process ([Restate timers](https://docs.restate.dev/develop/ts/durable-timers), [Cloudflare limits](https://developers.cloudflare.com/workflows/reference/limits/)); fleet-wide queries for runs awaiting input ([DBOS HITL](https://docs.dbos.dev/ai/hitl)); run-level dashboards and replay ([Vercel](https://vercel.com/docs/workflow), [Hatchet](https://hatchet.run/use-cases/ai-agents)).
- File-side properties with no engine analogue: the owner edits the definition and the state in the same medium with no deployment ("Editing the plan file (flipping a status or deleting a row) changes what the next run does" — [Cidre](https://adriacidre.com/blog/there-is-no-workflow-engine/)); versus engines where in-place edits of a deployed definition are unsafe ([Restate versioning](https://docs.restate.dev/operate/versioning), [Temporal](https://docs.temporal.io/workflow-definition)). Vercel's human-review guidance — "Confirm that the request still matches the version they reviewed, and record the approval separately from execution" ([Vercel concepts](https://vercel.com/docs/workflows/concepts)) — is a governance step the markdown loop gets for free because the approval line sits inside the reviewed document.
- Vercel's `durable-harness` for Claude Code/Codex/OpenCode/Pi persists the *agent session* "so sessions can resume after crashes and deployments" ([Vercel docs](https://vercel.com/docs/workflow)); Cloudflare's Pi Durable harness keeps a run going via the Lifecycle job queue after eviction ([Cloudflare Agents](https://developers.cloudflare.com/agents/)) — both durably hold the harness's transcript, not an owner-edited document.

### Inferences
- Mapping, pass by pass: engine *step* = one pass's model call; engine *journal* = the markdown document plus git history; engine *signal/hook* = the owner writing the gate line; engine *timer* = nothing — the markdown loop has no clock, it waits until someone runs the next pass; engine *versioning* = editing the template, which is free in markdown and a controlled deployment in an engine; engine *dashboard* = `ls`/`git log`.
- What the markdown loop is actually missing, in engine terms, is (a) a durable timer (nothing wakes it; the owner does), (b) atomic write of "pass output + pass marked done" (a crash between model return and file write loses one model call), and (c) serialized access if two processes ever run the same loop. For one operator with days between passes, (a) is a feature, (b) costs one re-run, and (c) does not arise. This matches Cidre's own threshold: add an engine when you "can name the specific durability problem it solves for you."
- What the engines are actually missing, in markdown terms, is a definition the owner can edit mid-run without a compatibility ritual, and a state the owner can read and correct by hand. The engines' own documentation treats both as hazards (RT0016, non-deterministic error, pinned deployments), not features.
- The closest engine-side equivalents to the user's setup are not the replay engines at all but (i) Vercel's/Cloudflare's harness-durability layers (which persist a coding-agent session) and (ii) Airflow 3.3's `awaiting_input` task state (a scheduled pass that parks until a human responds) — and both still hold the definition as code.

### Gaps
- No source opened describes an engine whose approval primitive is "the state document changed"; a file-watcher-to-signal bridge is an inference, not a documented pattern.
- No opened source quantifies how often a single-operator file loop loses work to the crash-between-output-and-write window.
