## Q1. Anthropic "Building effective agents" (Dec 19, 2024): workflows vs agents, the five patterns, and when not to use agents

### Takeaway
The foundational taxonomy: a *workflow* is LLM calls on predefined code paths; an *agent* is an LLM that directs its own process and tool use. The authors' core advice is to not build an agent unless a single augmented call or a workflow has failed; agents buy flexibility at the cost of latency, cost, and compounding error, and must be bounded by stopping conditions and sandboxed testing.

### Cited Findings
- Definitions: workflows are "systems where LLMs and tools are orchestrated through predefined code paths"; agents are systems where LLMs "dynamically direct their own processes and tool usage." — [Anthropic, Building effective agents, Dec 19 2024](https://www.anthropic.com/engineering/building-effective-agents)
- Patterns and what each buys (per the post): **prompt chaining** splits a task into sequential calls with optional programmatic checks between steps, trading latency for accuracy, for tasks that "can be easily and cleanly decomposed into fixed subtasks"; **routing** classifies input and sends it to a specialised prompt/model (separation of concerns); **parallelization** is either *sectioning* (independent subtasks run at once) or *voting* (same task run several times for confidence); **orchestrator-workers** has a central LLM decompose at runtime, delegate, and synthesise, for tasks whose subtasks cannot be predicted (the post's example is multi-file code changes); **evaluator-optimizer** pairs a generator with an evaluator in a loop, fitting when "evaluation criteria are clear and iterative refinement measurably helps." — [same](https://www.anthropic.com/engineering/building-effective-agents)
- When not to use agents (verbatim): "finding the simplest solution possible, and only increasing complexity when needed"; this "might mean not building agentic systems at all"; "optimizing single LLM calls with retrieval and in-context examples is usually enough"; frameworks "can also make it tempting to add complexity when a simpler setup would suffice." — [same](https://www.anthropic.com/engineering/building-effective-agents)
- Loop shape for agents: begins with a human command or discussion; the agent plans and operates independently; at each step it should gain "ground truth" from the environment (tool results, code execution); it can "pause for human feedback at checkpoints or when encountering blockers"; tasks end on completion, but "it's often common to include stopping conditions (such as a maximum number of iterations) to maintain control." — [same](https://www.anthropic.com/engineering/building-effective-agents)
- Stated costs: agentic systems "often trade latency and cost for better task performance"; autonomy means "higher costs, and the potential for compounding errors"; the authors recommend "extensive testing in sandboxed environments, along with the appropriate guardrails." For coding, tests verify functionality, but "human review remains crucial." — [same](https://www.anthropic.com/engineering/building-effective-agents)
- The page now carries a note that much of the tooling landscape has changed since publication. — [same](https://www.anthropic.com/engineering/building-effective-agents)

### Inferences
- In this taxonomy, a human-gated multi-pass document loop is a *workflow* at the outer layer (fixed phases, a human checkpoint between rounds) wrapping an *agent* at the inner layer (the orchestrator choosing tools within a round). The evaluator-optimizer pattern is the closest named analogue to "owner answers, orchestrator revises."
- The post's own stop condition for agents is weak (task completion or an iteration cap); every later architecture surveyed below is largely an attempt to strengthen it.

### Gaps
- The post gives no guidance on where state should live between iterations; that question only appears in the 2025 posts.

## Q2. Anthropic harness posts: long-running agents (Nov 26, 2025), context engineering (Sep 29, 2025), multi-agent research (Jun 13, 2025), and the Claude Code best-practices page (current as of Nov 2026)

### Takeaway
Anthropic's harness pattern is "initializer agent + repeated fresh-context coding agent, with all state in files and git": a JSON feature list the model may only flip from failing to passing, a progress log, an init script, descriptive commits, one feature per session, and self-verification before marking done. The reported failure modes are premature "victory," undocumented half-built state, premature "feature done," and time lost rediscovering how to run the app. The Claude Code docs now add three harness-level stop mechanisms (`/goal`, Stop hooks, `/loop`) and explicitly deprecate "keep going, don't be lazy" prompting.

### Cited Findings

**Effective harnesses for long-running agents (Nov 26, 2025, Justin Young)**
- Problem: agents work in discrete sessions with no memory of earlier ones; compaction alone was not enough, and even Opus 4.5 in a loop "fell short of a production-quality app from a high-level prompt." Two failure patterns: the agent "tried to do too much at once," running out of context mid-feature and leaving a half-built, undocumented feature; and a later agent that saw progress and "declare[d] the job done" too early. — [Anthropic, Effective harnesses for long-running agents, Nov 26 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Architecture: an **initializer agent** (first session, special prompt) sets up the environment; a **coding agent** runs every later session. "The two differ only in their initial user prompts"; system prompt, tools, harness are identical. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Where state lives: a feature list in **JSON** (200+ features, all initially "failing"), chosen because the model "is less likely to inappropriately change it than Markdown"; `init.sh` to start the dev server; `claude-progress.txt` as a log; a git repo with an initial commit and descriptive commits after each change. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Unit of iteration and session protocol: each session starts with `pwd`, reads git log and progress files, reads the feature list, picks "the highest-priority unfinished feature," starts the server via `init.sh`, runs a basic end-to-end test to catch a broken state; it ends with a descriptive commit and a progress update, "leaving the code in a clean state." — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Rules given to the agent: one feature at a time; edit the feature list only by changing the `passes` field; "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"; test as a human user would with browser automation; mark a feature passing only after careful verification; use git to revert bad changes. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Failure-mode table (verbatim rows): "Claude declares victory on the entire project too early" (fix: structured feature list, one feature per session); "Claude leaves the environment in a state with bugs or undocumented progress" (fix: git history, progress notes, basic test at session start); "Claude marks features as done prematurely" (fix: self-verify before marking passing); "Claude has to spend time figuring out how to run the app" (fix: `init.sh`). — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Generalization statement: the demo "is optimized for full-stack web app development"; the authors suggest "some or all of these lessons can be applied" to scientific research or financial modelling, presented as a future direction, and call the design "one possible set of solutions." Open questions: single general agent vs multi-agent; untested specialised testing/QA/cleanup agents; vision limits ("can't see browser-native alert modals through the Puppeteer MCP"). — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**Effective context engineering for AI agents (Sep 29, 2025)**
- Definition: context engineering is "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference." Core principle: "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." — [Anthropic, Effective context engineering, Sep 29 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Context rot": as tokens grow, "the model's ability to accurately recall information from that context decreases"; models have an "attention budget" depleted by every token; a "performance gradient rather than a hard cliff." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Three long-horizon techniques: **compaction** (summarise and restart; "typically serves as the first lever"; tune for recall first, then precision; clearing old tool results is the safest form); **structured note-taking / agentic memory** (the agent "regularly writes notes persisted to memory outside of the context window," e.g. NOTES.md or to-do lists; "excels for iterative development with clear milestones"); **sub-agent architectures** (specialised sub-agents in clean contexts; each "returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)"; suits "complex research and analysis where parallel exploration pays dividends"). — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Just in time" context: keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load at runtime; progressive disclosure lets agents "incrementally discover relevant context through exploration." Claude Code is a hybrid: CLAUDE.md loaded up front, glob/grep at runtime; the authors suggest the hybrid may suit "less dynamic" domains such as legal or finance. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Stated failure modes: runtime exploration is slower; an unguided agent "can waste context by misusing tools, chasing dead-ends"; aggressive compaction can lose "subtle but critical context"; bloated tool sets create ambiguity; vague prompts vs brittle hardcoded logic; guidance is "do the simplest thing that works." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**How we built our multi-agent research system (Jun 13, 2025)**
- Shape: "an orchestrator-worker pattern, where a lead agent coordinates the process" and delegates to parallel subagents; subagents return findings; a CitationAgent runs at the end. The lead saves its plan "to Memory to persist the context" because context past 200k tokens is truncated; the post recommends "artifact systems where specialized agents can create outputs that persist independently," with subagents storing work externally and passing lightweight references back. — [Anthropic, Multi-agent research system, Jun 13 2025](https://www.anthropic.com/engineering/multi-agent-research-system)
- Delegation rules: each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; effort-scaling rules are embedded in prompts (simple fact-finding "just 1 agent with 3-10 tool calls"; complex research 10+ subagents). — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Costs and results: agents use ~4x the tokens of chat and multi-agent ~15x; token usage alone explained 80% of BrowseComp variance; Opus 4 lead with Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on the internal eval; up to 90% time reduction for complex queries. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Failure modes (verbatim): early agents "spawning 50 subagents for simple queries," "scouring the web endlessly for nonexistent sources," "distracting each other with excessive updates," "agents continuing when they already had sufficient results"; duplicate work where subagents "performed the exact same searches as other agents." — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Explicit non-fit: domains that need "all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today"; "most coding tasks involve fewer truly parallelizable tasks than research." — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Reliability: resume "from where the agent was when the errors occurred," retry logic, regular checkpoints, rainbow deployments; evaluation is end-state ("whether the agent reached the correct outcome," not "whether the agent followed a specific process"). — [same](https://www.anthropic.com/engineering/multi-agent-research-system)

**Claude Code best practices (the Apr 2025 anthropic.com post now 308-redirects to code.claude.com/docs/en/best-practices; the page is undated but references Opus 5.5 and Claude Code v2.1.x, so it is the current Nov 2026 revision, not the original)**
- Two kinds of instruction: "Non-deterministic: you write the instruction, and Claude (the model) reads it ... there's no *guarantee* that it'll follow your instructions" vs "Deterministic: you configure the instruction, and Claude Code (the harness) *has* to execute this. This can be a hook, a deny rule, or a managed setting." Rule: "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices)
- The done-signal mapping: for "When it's done," the non-deterministic options are "A request for evidence, `/goal`, `/code-review`" and the deterministic ones are "Tests, typecheck, a `Stop` hook, CI." — [same](https://code.claude.com/docs/en/best-practices)
- Verification principle (verbatim): "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on. In practice that makes you the test suite"; "Give Claude something it can run that comes back pass or fail. Once it has that, it can keep going on its own and you don't have to watch." The check "can be almost anything, as long as Claude can read the result": a test file, a browser screenshot next to the mockup, etc. — [same](https://code.claude.com/docs/en/best-practices)
- Strictness ladder: in-prompt ("Claude decides for itself when it's satisfied"); `/goal` ("a condition that a separate model checks against the conversation after every turn"); a Stop hook (exit code 2 "sends Claude back to work," enforced by the harness, until the block cap of eight consecutive blocks with no tool call); and review "By someone who didn't write the code" (`/code-review` in "a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code"). Always ask for *evidence*: "'All tests pass' on its own tells you very little." — [same](https://code.claude.com/docs/en/best-practices)
- Reviewer over-finding warning: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." — [same](https://code.claude.com/docs/en/best-practices)
- Unattended-run checklist (verbatim): "Before a run goes unattended, make sure it knows what done looks like, can check its own work, and can only touch what it should. Give it a cap on turns or spend, and have a person approve the result at the end." Three questions: "Does it know what done looks like? A goal condition, a spec file, or a failing test"; "Can it check its own work?"; "What's it allowed to touch?" — [same](https://code.claude.com/docs/en/best-practices)
- How a loop starts: "The one thing it can't do is decide to *start*, so something has to: you, a timer, or an event." `/loop 15m ...` repeats a prompt on an interval; `claude -p` runs once "in CI jobs, git hooks, and shell loops"; `--bare` skips hooks/skills/CLAUDE.md for reproducible batch runs that reply `OK` or `FAIL`. — [same](https://code.claude.com/docs/en/best-practices)
- Course correction: "Watch the first minute, press `Esc` the moment Claude drifts, and after two failed corrections run `/clear` and write a better prompt instead of a third"; `/rewind` rolls code and/or conversation back to an earlier prompt. — [same](https://code.claude.com/docs/en/best-practices)
- Explicitly retired advice (table "what changed"): "The context window is your main constraint, manage it aggressively" (now: 1M windows and auto-compaction, "running out is rare"); "Use subagents to protect your context window" (now: "Running out of context is rarely the problem anymore"); "Delegate to a subagent for a better answer" ("Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help"); "Tell Claude to keep going, loop until done, don't be lazy" ("lines like that are more likely to cause over-work than fix a stall ... for runs nobody's watching, `/goal` or a `Stop` hook enforces it"); and "Describe your architecture and file layout in `CLAUDE.md`." — [same](https://code.claude.com/docs/en/best-practices)
- Subagent economics: a fresh subagent "first has to gather context your conversation already had, so it can end up *slower*"; a custom subagent with only `tools: Read, Grep, Glob` is "a reviewer that can't edit anything, and that limit is enforced by Claude Code rather than requested in a prompt." — [same](https://code.claude.com/docs/en/best-practices)

**Claude Code `/goal` docs (current; cites v2.1.234-2.1.269)**
- Mechanism: "`/goal` is a wrapper around a session-scoped prompt-based Stop hook. Each time Claude finishes a turn, Claude Code sends the condition and the conversation so far to your configured small fast model," which returns **Not yet met** / **Met** / **Impossible** with a reason. "completion is decided by a fresh model rather than the one doing the work." — [Claude Code docs, /goal](https://code.claude.com/docs/en/goal)
- Limits of the evaluator (verbatim): "It doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate." Good conditions have "One measurable end state," "A stated check," and "Constraints that matter"; bound runs with "or stop after 20 turns." Stall detection: "If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop." — [same](https://code.claude.com/docs/en/goal)
- Comparison table: `/goal` next turn starts when the previous one finishes, stops when the evaluator says met/impossible or an unrecoverable error; `/loop` starts on a time interval, stops when "You stop it, or Claude decides the work is done"; a Stop hook fires after every turn and "Your own script or prompt decides." — [same](https://code.claude.com/docs/en/goal)

**Claude Code sub-agents docs (current)**
- "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions"; use one "when a side task would flood your main conversation ... the subagent does that work in its own context and returns only the summary." Explore and Plan are "read-only tools; Write and Edit are denied"; custom `tools:` allowlists are harness-enforced; `isolation: worktree` gives an isolated checkout. Use the main conversation when "The task needs frequent back-and-forth or iterative refinement" or "Multiple phases share significant context." Nesting is allowed "up to three layers below the main conversation"; the concurrency default is 20. Warning: "Running many subagents that each return detailed results can consume significant context." — [Claude Code docs, Subagents](https://code.claude.com/docs/en/sub-agents)

### Inferences
- Anthropic's three posts converge on one state model: durable truth in files (JSON for anything the model must not casually rewrite, markdown for narrative notes, git for history), and conversation treated as disposable. The Nov 2025 post's JSON-vs-Markdown remark is the most direct published evidence for "put gate state in a structured file, not prose."
- The best-practices page's "done" ladder is a precise design vocabulary for human gates: in-prompt (model decides) → separate-model judge (`/goal`) → deterministic script (Stop hook) → a reviewer who never saw the reasoning. A human-written line in a document is a fourth, strictly stronger rung the docs do not name but which the "have a person approve the result at the end" line presupposes.
- The retired-advice table (Nov 2026) is important for anyone citing the 2025 posts: Anthropic has itself walked back "manage context aggressively," "subagents to protect context," and "tell it to keep going."

### Gaps
- The original Apr 2025 anthropic.com best-practices text is no longer served; I could not confirm which of its workflow recipes (explore-plan-code-commit, tests-first, screenshot iteration, safe YOLO, multi-Claude writer/reviewer) survive verbatim. The current page keeps the ideas (visual target, fresh reviewer, worktrees, headless fan-out) in new wording.
- Anthropic's Nov 2025 post does not report token or dollar cost for the long-running harness.

## Q3. OpenAI "Harness engineering: leveraging Codex in an agent-first world" (Feb 11, 2026, Ryan Lopopolo) and "Unrolling the Codex agent loop" (Jan 23, 2026)

### Takeaway
OpenAI's harness owns everything except the model: a repo that is the sole system of record (short AGENTS.md as a map; `docs/` for design docs, execution plans, quality grades), agent-legible feedback (bootable per worktree, Chrome DevTools, local logs/metrics/traces), mechanical enforcement of architecture via custom linters whose error messages carry remediation instructions, and scheduled "garbage collection" agents. Humans "steer," set acceptance criteria, and validate outcomes, but "aren't required to" review PRs. The authors explicitly say the end-to-end autonomy "should not be assumed to generalize without similar investment."

### Cited Findings
- Scale and constraint: "building and shipping an internal beta of a software product with 0 lines of manually-written code"; "on the order of a million lines of code"; "roughly 1,500 pull requests ... with a small team of just three engineers driving Codex"; first commit "late August 2025"; "Humans steer. Agents execute." — [OpenAI, Harness engineering, Feb 11 2026 (archive.org copy)](https://openai.com/index/harness-engineering/)
- The engineer's new job (verbatim): "design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work"; "Early progress was slower than we expected, not because Codex was incapable, but because the environment was underspecified"; when something failed "the fix was almost never 'try harder'"; the question is "what capability is missing, and how do we make it both legible and enforceable for the agent?" — [same](https://openai.com/index/harness-engineering/)
- The loop shape (verbatim): "Humans interact with the system almost entirely through prompts: an engineer describes a task, runs the agent, and allows it to open a pull request. To drive a PR to completion, we instruct Codex to review its own changes locally, request additional specific agent reviews both locally and in the cloud, respond to any human or agent given feedback, and iterate in a loop until all agent reviewers are satisfied (effectively this is a Ralph Wiggum Loop)." "Humans may review pull requests, but aren't required to." — [same](https://openai.com/index/harness-engineering/)
- Verification made agent-legible: "we made the app bootable per git worktree"; "wired the Chrome DevTools Protocol into the agent runtime"; logs/metrics/traces via a per-worktree ephemeral observability stack queryable with LogQL/PromQL so prompts like "ensure service startup completes in under 800ms" become tractable; "single Codex runs work on a single task for upwards of six hours." — [same](https://openai.com/index/harness-engineering/)
- Repo as context (verbatim): "give Codex a map, not a 1,000-page instruction manual." The one-big-AGENTS.md approach "failed in predictable ways: Context is a scarce resource ... Too much guidance becomes non-guidance ... It rots instantly ... It's hard to verify." So "A short AGENTS.md (roughly 100 lines) is injected into context and serves primarily as a map," with `docs/` as "the system of record" (design-docs with index and core-beliefs, exec-plans/active and completed plus tech-debt-tracker, product-specs, QUALITY_SCORE.md, etc.). "Plans are treated as first-class artifacts ... execution plans with progress and decision logs that are checked into the repository." "A recurring 'doc-gardening' agent scans for stale or obsolete documentation." — [same](https://openai.com/index/harness-engineering/)
- Legibility principle (verbatim): "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist. Knowledge that lives in Google Docs, chat threads, or people's heads are not accessible to the system." — [same](https://openai.com/index/harness-engineering/)
- Enforcement: "enforcing invariants, not micromanaging implementations"; fixed layers (Types → Config → Repo → Service → Runtime → UI) "enforced mechanically via custom linters (Codex-generated, of course!) and structural tests"; "Because the lints are custom, we write the error messages to inject remediation instructions into agent context"; "When documentation falls short, we promote the rule into code." — [same](https://openai.com/index/harness-engineering/)
- Merge philosophy: "minimal blocking merge gates ... In a system where agent throughput far exceeds human attention, corrections are cheap, and waiting is expensive. This would be irresponsible in a low-throughput environment." — [same](https://openai.com/index/harness-engineering/)
- Human role: "We prioritize work, translate user feedback into acceptance criteria, and validate outcomes. When the agent struggles, we treat it as a signal: identify what is missing—tools, guardrails, documentation—and feed it back into the repository, always by having Codex itself write the fix." The autonomous feature loop ends with "Escalate to a human only when judgment is required." — [same](https://openai.com/index/harness-engineering/)
- Generalization caveat (verbatim): "This behavior depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment—at least, not yet." — [same](https://openai.com/index/harness-engineering/)
- Entropy (verbatim): "Codex replicates patterns that already exist in the repository—even uneven or suboptimal ones. Over time, this inevitably leads to drift." "Our team used to spend every Friday (20% of the week) cleaning up 'AI slop.' Unsurprisingly, that didn't scale." Fix: "golden principles" plus "a set of background Codex tasks that scan for deviations, update quality grades, and open targeted refactoring pull requests. Most of these can be reviewed in under a minute and automerged. This functions like garbage collection." — [same](https://openai.com/index/harness-engineering/)
- Stated unknowns (verbatim): "What we don't yet know is how architectural coherence evolves over years in a fully agent-generated system. We're still learning where human judgment adds the most leverage and how to encode that judgment so it compounds. We also don't know how this system will evolve as models continue to become more capable." "Our most difficult challenges now center on designing environments, feedback loops, and control systems." — [same](https://openai.com/index/harness-engineering/)
- The Codex inner loop (UNVERIFIED, from search snippets of the primary post): "Unrolling the Codex agent loop," Michael Bolin, Jan 23 2026: "This process repeats until the model stops emitting tool calls and instead produces a message for the user"; "each turn always ends with an assistant message, which signals a termination state in the agent loop ... control returns to the user"; "context window management is one of the agent's many responsibilities"; the sandbox developer message "applies only to the Codex-provided shell tool ... other tools, such as those provided from MCP servers, are not sandboxed by Codex." — [OpenAI, Unrolling the Codex agent loop, Jan 23 2026](https://openai.com/index/unrolling-the-codex-agent-loop)
- Critical reception (HN, submitted Jun 5 2026, 297 points, 206 comments): "I would never dare put that in production"; "This would be much more convincing if the repos, issue trackers, etc. were accessible"; "why is massive amount of code generated is a flex?"; a worry about long-run blindspots: "Let's say that this repository goes on for years, at which point the docs folder is several MB in size. Would Codex be able to think outside of the box?"; and an endorsement listing the same recipe ("Give Claude/Codex a way to verify its own work ... Keep all context (issue tracking, docs, ideas, plans, worklogs) in-repo"). — [HN thread 48416264](https://news.ycombinator.com/item?id=48416264)
- Fowler-site framing (Birgitta Böckeler, Apr 2, 2026; a search result dates it Feb 17, 2026, which conflicts with the page date I read): harness = "everything in an AI agent except the model itself," Agent = Model + Harness; harness elements split into **guides** (feedforward, "steer it *before* it acts") and **sensors** (feedback, "observe *after* the agent acts and help it self-correct"), each either computational (linters, tests) or inferential (LLM review). Open questions she lists: keeping guides and sensors coherent as the harness grows; "Whether sensors that never fire indicate high quality or weak detection"; "The behavioural harness (functional correctness) remains largely unsolved"; "Building this outer harness is emerging as an ongoing engineering practice, not a one-time configuration." — [martinfowler.com, Harness Engineering](https://martinfowler.com/articles/harness-engineering.html)

### Inferences
- The OpenAI loop's unit of iteration is the PR, the orchestrator is the Codex agent itself driven by a human prompt, state lives entirely in the repo (code, docs/, exec-plans with decision logs), and the stop condition is "all agent reviewers are satisfied" plus CI. Human entry is at prompt time and at optional review; escalation is model-initiated.
- "Plans are first-class artifacts with progress and decision logs checked in" is the closest published analogue to a morphing document with an append-only changelog. OpenAI also pairs it with a *doc-gardening* agent, which is the piece a document loop usually lacks: something that detects staleness in the running document.
- Böckeler's guides/sensors split is a useful audit vocabulary: a human gate line in a document is a sensor that is inferential (a person judges) and manual; nothing in the OpenAI design has a sensor that is manual by construction.

### Gaps
- I could not open "Unrolling the Codex agent loop" itself; quotes come from search-result snippets and should be treated as UNVERIFIED in wording.

## Q4. Simon Willison, "Designing agentic loops" (Sep 30, 2025) and "Embracing the parallel coding agent lifestyle" (Oct 5, 2025)

### Takeaway
Willison's criterion is that a loop is worth running when the problem has "clear success criteria" and needs trial and error, and is safe to run only when YOLO-mode risk is contained by sandboxing and budget-capped credentials. His follow-up names the real bottleneck: human review throughput, and he reviews and lands every change himself.

### Cited Findings
- Definition: an LLM agent is "something that runs tools in a loop to achieve a goal"; designing agentic loops means designing the tools and the loop. — [Willison, Designing agentic loops, Sep 30 2025](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/)
- Suitability criterion (verbatim where possible): problems should have "clear success criteria" where a good solution "is likely to involve (potentially slightly tedious) trial and error"; the signal is the thought "ugh, I'm going to have to try a lot of variations here"; "Not every problem responds well to this pattern." The post does not use the phrase "automated verification," but says "automated tests" are the common theme and a "good, cleanly passing test suite" greatly amplifies coding agents. Examples: debugging a failing test, SQL-index performance tests, dependency upgrades, container-size optimisation. — [same](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/)
- Safety: YOLO mode is "so dangerous" yet key to productivity; risks are bad shell commands, exfiltration of files/secrets, and machine-as-attack-proxy. Containers are "a reasonable risk to accept for most people"; his preferred option is a remote machine (Codespaces); Anthropic's quoted guidance is "use `--dangerously-skip-permissions` in a container without internet access"; credentials should be scoped to test/staging with "a tight budget limit" (his Fly.io key: dedicated org, $5 budget). He notes "Most people choose option 3" (accept the risk) and that it is "still a very fresh area." — [same](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/)
- Follow-up: "the natural bottleneck on all of this is how fast I can review the results"; "I can only focus on reviewing and landing one significant change at a time"; suited tasks are research ("without making modifications to a project that you plan to keep"), codebase explanation, small maintenance, well-specified work ("Code that started from your own specification is a lot less effort to review"), and scouting; unsuited: "Reviewing code that lands on your desk out of nowhere is a *lot* of work." Isolation by fresh checkout in `/tmp`; Docker is "an aspiration." — [Willison, Parallel coding agent lifestyle, Oct 5 2025](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)

### Inferences
- Willison's loop has no persistent state design at all: state is the working tree, the stop condition is the test suite, and the human enters only at the start (goal) and end (review). That is why his criterion is so narrow; without an automatic pass/fail the loop has nothing to iterate against.

### Gaps
- Willison does not give explicit examples of unsuitable problems in the Sep 30 post; the "unsuitable" list above is inferred from the Oct 5 post.

## Q5. Geoffrey Huntley's Ralph loop (Jul 14, 2025; Jan 17, 2026) and Anthropic's ralph-wiggum / ralph-loop plugin (added Nov 16, 2025; moved Oct 26, 2026)

### Takeaway
Ralph is `while :; do cat PROMPT.md | claude-code ; done`: a deterministic outer loop around a fresh-context agent whose only memory is files and git, with a human tuning PROMPT.md "like a guitar." Huntley says it works for greenfield bootstrapping to "90%," breaks on existing codebases, duplicates work when search misleads it, and ships placeholder code; Anthropic's plugin turns the bash loop into a same-session Stop hook with `--max-iterations` and an exact-match `--completion-promise`, and its README says it is "Not good for: Tasks requiring human judgment or design decisions."

### Cited Findings
- The loop: `while :; do cat PROMPT.md | claude-code ; done`. Files: `PROMPT.md` (piped in every iteration), `specs/` (one spec per file, written after a long conversation before building), `fix_plan.md` (prioritised plan, regenerated often, sometimes deleted entirely), `AGENT.md` (how to build/run; the agent updates it). — [Huntley, Ralph, Jul 14 2025](https://ghuntley.com/ralph/)
- Why it works (verbatim): "deterministically bad in an undeterministic world"; each loop starts with a new context window; Ralph can "loop back on its own output" and log bugs into `fix_plan.md`. Human role: watch for bad patterns and add "signs" to the prompt ("Each time Ralph does something bad, Ralph gets tuned - like a guitar"); decide to `git reset --hard` or write rescue prompts. — [same](https://ghuntley.com/ralph/)
- Stop condition: `while :` has none; "Eventually, Ralph will run out of things to do in the TODO list"; it may "go completely off track." Rule: "One item per loop. I need to repeat myself here—one item per loop" (relaxable later; note his own build prompt says "choose the most important 10 things"). — [same](https://ghuntley.com/ralph/)
- Stated limitations (verbatim): "It has defects, but these are identifiable and resolvable through various styles of prompts"; "The more you use the context window, the worse the outcomes you'll get" (~170k budget); ripgrep misses lead Ralph to wrongly conclude code is unimplemented and duplicate it, "the Achilles' heel of Ralph"; "Claude has the inherent bias to do minimal and placeholder implementations"; "you'll wake up to a broken codebase that doesn't compile from time to time"; "There's no way in heck would I use Ralph in an existing code base"; expect "90% done." — [same](https://ghuntley.com/ralph/)
- Follow-up "everything is a ralph loop" (Jan 17, 2026): Ralph is "an orchestrator pattern where you allocate the array with the required backing specifications and then give it a goal then looping the goal"; it is "monolithic," "a single process that performs one task per loop," and "GENERIC and can be used for ALL TASKS"; "It's important to *watch the loop* as that is where your personal development and learning will come from"; against multi-agent communication "At this stage, it's not needed"; non-deterministic agents as microservices would be "a red hot mess." — [Huntley, everything is a ralph loop, Jan 17 2026](https://ghuntley.com/loop/)
- Plugin history: `plugins/ralph-wiggum` was added to anthropics/claude-code on 2025-11-16 ("feat: Add ralph-wiggum plugin for iterative self-referential development"), patched 2026-01-05/06, and on 2026-10-26 moved out ("Install marketplace plugins from claude-plugins-official"); the marketplace now lists it as `ralph-loop`, author Daisy Hollman (Anthropic), source `anthropics/claude-plugins-official/plugins/ralph-loop`. — [anthropics/claude-code commit history for plugins/ralph-wiggum](https://github.com/anthropics/claude-code/commits/main/plugins/ralph-wiggum); [marketplace.json](https://github.com/anthropics/claude-code/blob/main/.claude-plugin/marketplace.json)
- Plugin mechanism (README verbatim): "This plugin implements Ralph using a **Stop hook** that intercepts Claude's exit attempts"; "The loop happens **inside your current session** - you don't need external bash loops"; "The prompt never changes between iterations / Claude's previous work persists in files / Each iteration sees modified files and git history." Options: `--max-iterations <n>` (default: unlimited), `--completion-promise <text>`; `/cancel-ralph`. — [ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)
- Plugin limits (verbatim): "Always use `--max-iterations` as a safety net to prevent infinite loops on impossible tasks"; "The `--completion-promise` uses exact string matching, so you cannot use it for multiple completion conditions (like 'SUCCESS' vs 'BLOCKED'). Always rely on `--max-iterations` as your primary safety mechanism." "Not good for: Tasks requiring human judgment or design decisions / One-shot operations / Tasks with unclear success criteria / Production debugging." "Good for: ... Tasks with automatic verification (tests, linters)." Philosophy: "Operator Skill Matters: Success depends on writing good prompts, not just having a good model." — [same](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)
- A practitioner note: one iteration "equals one complete session cycle, not one tool call or one TODO item"; "Claude will happily burn through all your tokens"; caution for "Tasks that need frequent human judgment" and "Workflows where errors compound." — [Looking4OffSwitch, Jan 4 2026](https://looking4offswitch.github.io/blog/2026/01/04/ralph-wiggum-claude-code)
- Critics: David Factor (Jan 12, 2026): "The loop is the easy part"; "A loop without a reliable 'better / worse' signal isn't optimisation"; Ralph "just tries more, and you pay for the difference"; "the judgment still lands on a human reviewer," after compute is spent; reported ~US$14k spend on Huntley's "cursed" project from the HN discussion; his escalation ladder puts Ralph last, "only when success is checkable, failures are actionable, regressions can be rejected, and cost is bounded." — [Factor, The Ralph Wiggum Loop Isn't a Strategy](https://piperstreetsoftware.pages.dev/articles/ralph-loop-isnt-a-strategy.html). xr0am (Jan 24, 2026): "There's no task orchestration. No dependency tracking. No tool permissions"; "Ralph's markdown approach requires the agent to infer these relationships from prose"; fix is JSON tasks with explicit dependency arrays. — [xr0am, What Ralph Wiggum loops are missing](https://xr0am.substack.com/p/what-ralph-wiggum-loops-are-missing)

### Inferences
- The bash loop and the plugin differ on exactly the axis that matters for a document loop: Huntley resets context every iteration (memory = files only); the plugin keeps one session, so iterations accumulate context and the only memory discipline is what the prompt enforces. Huntley's "the more you use the context window, the worse" argues for the bash form on long runs.
- The plugin's exact-match completion promise is the weakest stop mechanism in this survey (a string the model emits); `/goal` (a separate judge) and Stop hooks (a script) were Anthropic's later answers to the same problem.
- xr0am's complaint (prose state forces the agent to infer task relationships) is the same point as Anthropic's JSON-over-Markdown choice, arrived at independently.

### Gaps
- The $14k figure is secondhand (Factor citing HN); I did not open the HN thread it refers to.
- The plugin README's "Real-World Results" ($50k contract for $297; six repos overnight) are unsourced in the README.

## Q6. 2026 "loop engineering," outer vs inner loop, and Karpathy's autoresearch (Mar 7, 2026)

### Takeaway
By mid-2026 the practitioner consensus has shifted from "write the prompt" to "write the loop," with three recurring rules: the agent that did the work must not grade it; the loop is only as good as its verifier; and cap iterations and spend. Karpathy's autoresearch is the purest instance: a `program.md`, one editable file, a fixed 5-minute budget, a single scalar metric, git keep/revert, and "LOOP FOREVER" until the human interrupts; Karpathy himself (per secondary reporting) limits it to tasks with quantitative evaluation.

### Cited Findings
- autoresearch repo: "AI agents running research on single-GPU nanochat training automatically"; "the agent modifies the code, trains for 5 minutes, checks if the result improved, keeps or discards, and repeats"; files are `prepare.py` (fixed, not modified by the agent), `train.py` ("the single file the agent edits"), `program.md` (instructions, "edited and iterated on by the human"; "a super lightweight 'skill'"); "you are programming the `program.md` Markdown files." Metric: `val_bpb`, lower is better. 99.2k stars at time of reading. Limits stated: single NVIDIA GPU required; fixed time budgets are comparable within a platform only. — [karpathy/autoresearch README](https://github.com/karpathy/autoresearch)
- program.md loop rules: create branch `autoresearch/<tag>` ("must not already exist — this is a fresh run"); `results.tsv` with header only, untracked by git; each run is a fixed 5-minute budget; modify `train.py`, commit, run to `run.log`, grep `val_bpb` and `peak_vram_mb`; "Keep the commit if `val_bpb` improved. If it's equal or worse, reset back to the starting commit"; the first run is the unmodified baseline; "LOOP FOREVER," do not pause to ask whether to continue, stop only when the human interrupts; forbidden to modify `prepare.py` or the `evaluate_bpb` harness or add dependencies; "a tiny gain that adds messy complexity is probably not worth keeping"; runs over 10 minutes are killed and treated as failures. — [karpathy/autoresearch program.md](https://github.com/karpathy/autoresearch/blob/master/program.md)
- Karpathy on scope (UNVERIFIED verbatim; reported by Gigazine, Mar 24, 2026): autoresearch is "only effective when quantitative evaluation is possible" (paraphrase); not suited to tasks "requiring human judgment, creativity, or subjective assessment"; "To make the most of the tools currently available, you must not be the bottleneck"; he ran 700+ experiments; Shopify's Lütke reported 37 experiments overnight and a 19% gain; Harrison Chase forked it as "autoresearch for agents" using LangSmith evals. — [Gigazine, Mar 24 2026](http://gigazine.net/gsc_news/en/20260324-humans-bottleneck-ai)

- Steinberger (UNVERIFIED; X post Jun 7, 2026, not opened): quoted by Pulumi as "Here's your monthly reminder that you shouldn't be prompting coding agents anymore" and by a German translation of mvanhorn's thread as "you should design loops that prompt your agents." ### Inferences
- Across Osmani, Diri, Mitra, mvanhorn and Factor, the 2026 rules are the same three: (1) maker and judge must be different contexts (ideally a deterministic script), (2) no verifier means no loop, (3) hard caps on iterations and spend. ## What would stop this from managing something other than code

### Takeaway
The published architectures lean on four things code supplies for free and most other artifacts do not: an executable pass/fail oracle, a diffable and revertable state store, a dependency structure that can be mechanically enforced, and a closed world where "anything not in the repo doesn't exist" is acceptable. Remove any one and the loop's stop condition, its memory, or its error-containment story has to be re-engineered by hand.

### Cited Findings
- The oracle is the whole design, by the authors' own account: Anthropic: "If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on." — [Claude Code best practices](https://code.claude.com/docs/en/best-practices). Willison: "clear success criteria" plus trial and error. — [Willison](https://simonwillison.net/2025/Sep/30/designing-agentic-loops/). Ralph plugin: "Not good for ... Tasks requiring human judgment or design decisions ... Tasks with unclear success criteria." — [ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop). Mitra: "Loops do not create signal that is not there." — [Mitra](https://subhadipmitra-site.pages.dev/blog/2026/loop-engineering-verifier/). Karpathy (secondary): quantitative evaluation only. — [Gigazine](http://gigazine.net/gsc_news/en/20260324-humans-bottleneck-ai)
- Even the model-judged stop condition assumes evidence surfaces in the transcript: `/goal`'s evaluator "doesn't run commands or read files independently." — [Claude Code docs, /goal](https://code.claude.com/docs/en/goal)
- Revertability and diffability: Anthropic's harness relies on "git to revert bad changes and recover working states"; autoresearch on "reset back to the starting commit"; OpenAI on short-lived PRs where "corrections are cheap." — [Anthropic harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents); [autoresearch program.md](https://github.com/karpathy/autoresearch/blob/master/program.md); [OpenAI](https://openai.com/index/harness-engineering/)
- Mechanical enforcement of structure: OpenAI's dependency layers are "enforced mechanically via custom linters ... and structural tests" with error messages that "inject remediation instructions"; Böckeler lists the computational guides/sensors (linters, tests) as the deterministic half of a harness and says "The behavioural harness (functional correctness) remains largely unsolved" even for code. — [OpenAI](https://openai.com/index/harness-engineering/); [Böckeler](https://martinfowler.com/articles/harness-engineering.html)
- Closed-world assumption: "anything it can't access in-context while running effectively doesn't exist. Knowledge that lives in Google Docs, chat threads, or people's heads are not accessible." — [OpenAI](https://openai.com/index/harness-engineering/)
- Shared-context and dependency-heavy work is a stated non-fit for parallel subagents: "all agents to share the same context or involve many dependencies between agents are not a good fit." — [Anthropic multi-agent](https://www.anthropic.com/engineering/multi-agent-research-system)
- Drift is reported even with all of the above in place: "Codex replicates patterns that already exist in the repository—even uneven or suboptimal ones. Over time, this inevitably leads to drift." — [OpenAI](https://openai.com/index/harness-engineering/). Anthropic warns compaction "can lose subtle but critical context." — [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Human review, not generation, is the throughput limit: "the natural bottleneck on all of this is how fast I can review the results." — [Willison, Oct 5 2025](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/); OpenAI: "our bottleneck became human QA capacity." — [OpenAI](https://openai.com/index/harness-engineering/)
- The only published pattern that uses a human-readable plan as the reviewed artifact argues it works because the plan is short and upstream of the expensive output: "a bad line of a plan could lead to hundreds of bad lines of code"; "I *can* read 200 lines of a well-written implementation plan." — [HumanLayer ACE-FCA](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)

### Inferences (what breaks, mapped to a document loop with a human gate)
1. **Stop condition.** For a prose artifact there is no compiler, so the only rungs left on Anthropic's ladder are "separate model judges the transcript" and "a person approves." A human-written gate line is the strongest rung, but it means the loop cannot run unattended; the authors above all describe unattended loops as the point of the exercise. The practical consequence is that the loop's cadence is bounded by owner latency, exactly Willison's review bottleneck, moved from the end of the loop to every round.
2. **Verifier independence.** The 2026 rule "never let the maker grade its own work" is satisfiable without code: a reviewer subagent that never saw the orchestrator's reasoning (`/code-review`'s design) can grade a document against a spec. But Mitra's warning stands: an LLM judge without a rubric and ground truth is "a target rather than a verifier," so the gate criteria must be written down before the round, not inferred after.
3. **State.** Anthropic's JSON-over-Markdown finding and xr0am's "infer relationships from prose" critique both say a running markdown document is a poor place for machine-read state (which questions are open, which gates passed). The published fix is to split: narrative in markdown, control state (open questions, gate status, round number) in a structured file the model may only flip, plus an append-only log, which is what OpenAI's exec-plans with decision logs do.
4. **Revertability.** Code loops lean on git revert and short PRs. A morphing document needs an equivalent: per-round snapshots or a diffable changelog, or a bad round is irreversible in a way "reset back to the starting commit" is not.
5. **Drift and staleness.** OpenAI needed a scheduled "doc-gardening" agent because agent-written docs rot; a document that is repeatedly morphed by the same orchestrator will replicate its own earlier phrasing and framing (OpenAI's "replicates patterns that already exist") with no linter to catch it. No published source offers a non-code drift detector.
6. **Closed world.** OpenAI's legibility principle is a strength for code and a liability for documents whose truth lives in the owner's head: every published design pulls knowledge *into* the repo before looping; a question-and-answer loop is the mechanism for doing that, but nothing in the surveyed designs schedules it or bounds it (the research-system post's "scouring the web endlessly" and "spawning 50 subagents for simple queries" are the analogous failures).
7. **Subagent return discipline.** The "returns only a condensed summary (1,000–2,000 tokens)" and "no file writes for read-only roles" rules (Anthropic context post; sub-agent docs `tools:` allowlist) transfer directly to non-code; they are the parts of the published designs that do not depend on code at all.

### Gaps
- No primary source in this survey runs a loop over a document, policy, model, or plan with reported outcomes; Anthropic's "scientific research or financial modeling" is explicitly a future direction, and Horthy's RPI reviews plans only as a prelude to code.
- No source quantifies the cost of a human gate per round (owner latency vs tokens), so the claim that a gated loop is "slower but safer" is inference, not measurement.
